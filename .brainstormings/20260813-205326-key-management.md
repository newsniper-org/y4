# Key management deep-dive — key = capability, 측정-boot 에 sealed

## §0 프레임

**최종 구현 목표 기준.**  key 는 **crown jewels** — TCB 의 핵심.  key
management 는 여러 발제가 만나는 지점: attestation(AK/session/§7 binding) ·
side-channel(XChaCha20 masking) · capability model · capability-bound-alloc
(sealed zero-on-free).  본 발제가 Y4 의 **모든 key 의 종류·수명·격리·저장·
폐기**를 통합.

## §0.5 원칙 정합

- **atomic-free**(§0.5): key 연산은 context_switch / lease-switch 의 sequential
  trusted path, key 상태는 **partition-scoped single writer** — cross-CPU
  atomic 없음.
- **TCB 최소화**(원칙 1): key material 을 **hardware 보안 경계에 가둠**, host
  plaintext 노출 최소화.
- **capability**(원칙 2): ★ **key 접근 = capability**, ambient secret 아님
  (§2).
- **partition**: partition_id → key namespace(§3, master-key 확장).
- **formal-first**(원칙 6): ★ **경계** — key *management* 는 Verus, crypto
  primitive *강도* 는 trusted assumption(§9).

## §1 key 종류 (inventory)

| key | 용도 | 소유/저장 | 수명 |
|---|---|---|---|
| **XChaCha20 masking** (256-bit key/192-bit nonce) | accelerator 데이터 masking | WaveTensor 보안 영역(★ host 미노출) | per-context_switch nonce rebind |
| **AK** (attestation key) | quote 서명 | hardware RoT(TPM EK/AMD VCEK 체인) | 장기(플랫폼) |
| **session key** | tenant 채널 암호화 | 최소 TCB(sealed) | per-session(ephemeral) |
| **lease-scoped key** | tenant 데이터 at-rest/in-transit | partition zone | per-lease |
| **KEK** (key-encryption-key) | 하위 key seal/unseal | measured-boot 에 sealed | 부팅 |
| **boot-verify pubkey** | secure boot 서명 검증 | 불변(RoT/펌웨어) | 고정 |
| **TRNG entropy** | nonce/key 생성 seed | WaveTensor TRNG | 즉시 소비 |

## §2 (결정) key = capability — use-without-extraction ★

- key 접근 = **capability**(원칙 2), ambient secret 아님.
- raw key material 은 **직접 readable 하지 않는다** — capability 는 key 를
  *사용*(encrypt/decrypt/sign)하게 하되 *추출*은 못 함(TPM/HSM 모델).
- 타입 수준: key material = **sealed type**(opaque), **연산만 노출**.  손상된
  상위 코드도 key 를 유출 못 함(추출 경로 부재).

## §3 (결정) partition_id → key namespace — master-key 확장 ★

- 각 partition 의 key 는 **격리** — partition 이 타 partition key 접근 불가.
- `partition_id` 가 **key namespace 를 키함** — capability-bound-alloc zone →
  IOMMU domain → μarch(cache/TLB) → seL4 domain 에 이어 **crypto key** 추가.
- ⟹ "하나의 partition 모델, N enforcer" 에 **key isolation** 합류.  cross-tenant
  key 접근 = 구조적 불가.

## §4 (결정) key 계층 + 측정-boot sealing — attestation 결합 ★

**계층**:
```
hardware RoT (EK / AMD-SP — hardware 밖 안 나감)
   │  seal to PCR
   ▼
KEK (measured-boot 상태에 sealed — PCR 매칭 시만 unseal)
   │  KDF (per-partition/per-lease)
   ▼
per-partition key / per-lease key / session key
```
★ **sealing**: key 를 **measured 상태(PCR)에 bind** → **verified TCB 아래에서만
unseal**.  변조/손상된 TCB(측정 불일치)는 tenant key 를 **못 연다**.
⟹ **measured boot(attestation 발제)가 key 가용성을 gate** — "형식 증명된 seL4 +
올바른 Y4" 상태에서만 key 접근.  attestation 과 key management 의 직접 결합.

## §5 (결정) lifecycle — 생성 → 확립 → 사용 → 회전 → 폐기

- **생성**: WaveTensor **TRNG**(고엔트로피, unbiased).
- **확립**: session key = **forward-secret authenticated key agreement / KEM**
  (계약) + attestation §7 binding(session key ↔ quote — attested TCB 가 그
  key 를 쥠).  구체 원시요소(예: ECDHE)는 고정하지 않고 crypto agility 로 위임
  (§7/§8) — Y4 가 고정하는 건 "forward secrecy + attested" **성질**뿐.
- **사용**: XChaCha20 masking / session 암호화.
- **회전**: per-lease / **per-context_switch**(nonce rebind) / usage 한도(keystream
  상한) / fault·compromise 표시 시.
- **폐기**: **zeroization** — key material 잔존 0.  capability-bound-alloc 의
  **sealed zero-on-free 와 동형**(lease 종료 bulk reclaim 시 partition key 소거).

## §6 (결정) nonce management — XChaCha20-specific ★

- XChaCha20 **192-bit nonce** → **random nonce(TRNG) 안전** — birthday bound 가
  천문학적이라 counter 불요(96-bit ChaCha20 과 결정적 차이).
- **context_switch 시 nonce rebind**(wavetensor_terms).
- ★ **불변식**: **(key, nonce) 절대 재사용 금지** — keystream reuse = 파국
  (두 평문 XOR 노출).  §9 검증 핵심 대상.

## §7 (결정) crypto agility — hw_mechanism_abstraction 적용

- ★ **measurement-hash**(SHA-256/384 등) + **AK-signature**(ECDSA/EdDSA 등)
  알고리즘은 **TPM/RoT 가 제공하는 realization** → **`docs/hw_mechanism_
  abstraction.md` 정책 적용**: Y4 는 계약("측정 hash" / "quote 서명")만 고정,
  구체 알고리즘은 TPM/deployment 가 결정 + attestation 이 **어떤 알고리즘인지
  보고**(crypto agility).
- ★ **session 확립 key-agreement 도 crypto-agile**: Y4 는 "**forward-secret
  authenticated key agreement / KEM**" **계약만 고정**(§5/§8), 구체 원시요소
  (ECDHE / hybrid / ML-KEM)는 realization 으로 위임 + 협상·보고.  post-quantum
  이행이 이 agility 위에서 이뤄짐.
- **XChaCha20 masking 은 WaveTensor-owned**(외부 벤더 메커니즘 아님 →
  hw_mechanism_abstraction §3 경계) → Y4/WaveTensor 가 **고정**.  Y4 자신의
  산출물이므로 추상화-위임 대상 아님.

## §8 forward secrecy + post-quantum (forward-looking)

- **계약 = forward secrecy + authenticated**: session 확립은 후일 key 가
  유출돼도 과거 세션을 복호 못 하게(forward secrecy) + attested 여야 한다 —
  이 **성질**이 Y4 가 고정하는 것.  특정 원시요소가 아님.
- **realization 은 crypto-agile(§7)**, **KEM-중심** 프레이밍: **ECDHE(현재)
  → ECDHE+ML-KEM hybrid(과도기) → ML-KEM(FIPS 203, PQC)**.  ECDHE 는 *하나의*
  realization 예시일 뿐(forward-secrecy·PQC 세계는 DH 보다 KEM 이 미래지향적).
- **PQC 근거**: classical key agreement 는 양자 취약, attestation 신뢰가
  장기이므로 PQC-readiness 가 가치 — §7 crypto agility 가 이행 경로를 연다.

## §9 verification — ★ 경계

**Verus 가 증명(key management)**:
- **nonce uniqueness** — (key, nonce) 재사용 0(§6, keystream reuse 방지).
- **zeroization** — 폐기 후 key material 잔존 0(§5).
- **partition key isolation** — partition 이 타 partition key 접근 0(§3).
- **use-without-extraction** — raw material 미노출(§2, 타입 수준).

**★ 경계 — Verus 밖(trusted assumption)**:
- crypto primitive *강도*(예: XChaCha20 / 키합의(ECDH·ML-KEM 등) 의 수학적
  안전성 — 어떤 realization 을 쓰든)는 **증명 대상 아님** — seL4 처럼 trusted,
  side-channel §8 처럼 assumption.  Verus 는 "key 를 올바르게 다룬다"를 증명
  하지 "암호가 안전하다"를 증명하지 않는다.

## §10 결정 / 미결 요약

**결정 방향(강)**:
- **key = capability, use-without-extraction**(§2)
- **partition_id → key namespace**(master-key 확장, §3)
- **measured-boot sealing** — verified TCB 아래에서만 unseal(attestation 결합, §4)
- lifecycle: TRNG 생성 + ephemeral 확립(forward secrecy) + zeroization 폐기(§5)
- **(key, nonce) 유일 불변식**(§6)
- crypto agility = **hw_mechanism_abstraction 적용**(측정hash·AK서명·**session
  key-agreement**) — 계약만 고정("forward-secret authenticated agreement/KEM"
  등), ECDHE/hybrid/ML-KEM 는 realization; XChaCha20 masking 은 WaveTensor-owned
  고정(§7)
- Verus = key management, crypto 강도 = trusted assumption(§9)

**미결(설계 필요)**:
- WaveTensor 측 masking key 저장 위치(shadow region? HIU 내부?) — ⏳ hiu_abi

- session key-agreement **realization·migration 정책**(ECDHE → hybrid → ML-KEM
  전환 시점) — 계약은 §5/§7 결정, 구체 선택은 crypto agility 로 위임
