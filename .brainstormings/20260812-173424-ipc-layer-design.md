# IPC layer 설계 — atomic-free coordination substrate 로서의 IPC

## §0 프레임

**최종 구현 목표 기준** (allocator 시리즈와 동일 프레임).  현재 `ipc/`
크레이트 (18 tests, roadmap **stage 0**) 는 mock-backed baseline —
scheme+msgport verb 집합은 완비됐지만 실제 `Sel4Backend` 미결, per-CPU
sharding 미구현, 6개 assume() 가 trusted boundary 에 남아 있음.  본
문서는 그 stage 0 을 출발점으로 **최종 IPC 설계가 무엇을 지향하며, 어떤
설계 결정이 남아 있는지**를 탐색.

재사용 기반 (변경 없음): **Redox scheme verb**(제어평면) +
**DragonFly LWKT msgport**(데이터평면) hybrid — decision **I-P2**.

## §0.5 불가침 원칙 — atomic-free 를 IPC 로 확장 (★★★ 시리즈 관통 insight)

allocator §0.5 의 **atomic operation 배제**(불가침) 를 IPC 로 그대로
확장한다.  근거가 억지가 아니라 **LWKT 자체가 원래 atomic/lock 회피
설계**라는 점 — DragonFly LWKT msgport 는 "message 를 owner CPU 의
port 로 보내고 owner 가 자기 문맥에서 처리" 하는 per-CPU token-passing
구조로, 공유 자료구조를 atomic 으로 갱신하지 **않는** 것이 설계 목표.
Y4 IPC 는 이 원칙을 유지.

이로써 시리즈 전체를 관통하는 하나의 명제가 성립한다:

> **atomic-free composition** — Y4 의 어떤 subsystem 도 내부에서 atomic
> 을 쓰지 않으며(alloc §0.5), **subsystem 간 cross-CPU 협조 역시
> shared-memory atomic 이 아니라 message-passing(그 자체가 per-CPU·
> atomic-free 인 IPC)으로만** 이뤄진다.

Linux 는 cross-CPU 협조를 도처에서 atomic(percpu counter, RCU,
cmpxchg)으로 푼다.  Y4 는 **cross-CPU 협조의 유일한 통로를 IPC 로
단일화**하고, 그 IPC 를 atomic-free 로 유지한다.  귀결:

- **deterministic latency** — atomic contention/cache-line bouncing 부재
  (RT §2.1 정합, WCET 분석 가능)
- **Verus-only 검증** — 메모리 모델 개입 없이 순차 semantics 로 증명
  (Kani/loom 불요)
- **cross-platform 무료 이득** — arch memory model(AArch64 weak / POWER
  weaker) 회피 (cross-platform 문서 §IPC "independent" 의 실제 근거)

## §1 두 평면의 역할 분리 — 왜 hybrid 인가

| 축 | 제어평면 = **scheme** (Redox) | 데이터평면 = **msgport** (LWKT) |
|---|---|---|
| 대상 | namespace / capability lookup / 연결 수립 | 수립된 endpoint 상의 고빈도 message |
| 빈도 | 낮음 (coarse-grained) | 높음 (hot path) |
| verb | `register`/`lookup`/`open`/`close`/`dup`/`read`/`write`/`fevent` | `open`/`send`/`wait`/`forward`/`abort`/`reply`/`time_out` |
| 복사 | 작은 inline 복사 허용 (scheme buffer) | **zero-copy 지향** (caller-allocated, §4) |
| 대응 spec | SC1~SC4 + K3 | M1~M5 |

**왜 하나로 통합하지 않나.**  Redox 는 *모든 것*을 scheme(fd-유사)으로
표현하고, DragonFly 는 *모든 것*을 msgport 로 표현한다.  둘 다 단일 축의
극단.  Y4 는 **연결 수립·이름공간·capability 획득**(저빈도, 정책 결정)과
**메시지 전달**(고빈도, 기계적)을 분리해 각 축의 강점만 취한다 — scheme
의 명료한 namespace/capability semantics + msgport 의 per-CPU zero-copy
hot path.  이 분리는 RT(§5)에도 유리 — 정책 결정(scheme)과 데이터 경로
(msgport)의 WCET 를 독립적으로 분석.

## §2 cross-CPU free 위임의 실제 메커니즘 (★ open thread 회수)

allocator §2.1 이 IPC 로 넘긴 문제: **object 가 CPU A 의 slab 에서
할당됐는데 CPU B 에서 free 요청**될 때, allocator 내부에서 atomic
remote-free queue 로 풀지 **않고**(§0.5 위반) IPC 로 위임한다.  그
"위임" 이 구체적으로 무엇인지 여기서 확정 시도.

### 2.1 기본 흐름
```
CPU B: free(ptr)  where owner(ptr).cpu == A  (A ≠ B)
   │  allocator 는 ptr 을 자기(B) freelist 에 넣지 않는다 (§0.5)
   ▼
CPU B → msgport.send(port=A, FreeReq{ptr, size_class})   ← LWKT 패턴 그대로
   ▼
CPU A: 자기 critical section 에서 wait()/drain → 자기 freelist 로 반환
```
cross-CPU free 가 **정확히 LWKT 의 "owner CPU 로 message → owner 가
처리" 패턴**과 일치한다 — 즉 새 메커니즘이 아니라 msgport 의 기존 용법.

### 2.2 설계 질문 (미결)

- **(a) FreeReq 도 caller-allocated 여야 하나?** — C1(alloc 독립) 보존을
  위해 FreeReq 메시지는 **alloc 을 호출하면 안 된다**(무한 재귀:
  free 하려고 alloc 하면 모순).  → **고정 inline 슬롯 / per-CPU 예약 링**
  으로 구현해야.  **유력**: msgport 에 `FreeReq` 전용 bounded 고정
  용량 채널(alloc 무관).
- **(b) back-pressure** — CPU B 가 CPU A object 를 대량 free 하면 A 의
  FreeReq 채널이 포화.  거부(§0.5 정합, 실패 반환) vs blocking(RT 위반).
  → **유력**: bounded 채널 + 포화 시 **caller 가 local defer list 로
  보관**(B 자신이 잠깐 들고 있다 재시도) — atomic 없이 back-pressure.
- **(c) latency** — cross-CPU free 는 **async**.  메모리가 즉시
  owner 로 반환되지 않는다.  A 가 언제 drain 하나?  → context switch /
  wait() 경계 / bounded quantum 마다 drain.  RT §2.1: **drain 도
  bounded** 여야(1회 drain 당 처리량 상한).
- **(d) ordering / ABA** — 같은 ptr 이 A 에서 재할당되기 전에 FreeReq 가
  도착해야.  size_class + generation tag 로 stale FreeReq 방어.

### 2.3 tradeoff 명시
| | async free 위임 (Y4) | atomic remote-free queue (Linux/일반) |
|---|---|---|
| §0.5 | ✅ 준수 | ✗ 위반 |
| 반환 지연 | 있음 (owner drain 까지) | 없음 (즉시) |
| WCET | 분석 가능 (bounded drain) | atomic contention 으로 불확정 |
| throughput | 다소 낮음 | 높음 |

Y4 는 **deterministic > throughput** 이므로 지연을 수용.  이 tradeoff
자체가 paper 차별점(hard-RT hypervisor 의 allocator-IPC 통합 설계).

## §3 capability 전달 — Y4 고유 (capability microkernel 정합)

seL4 는 message 에 **capability 를 실어** 전달(IPC buffer 의 cap
transfer + `seL4_CNode_Mint`).  Y4 IPC 는 이를 1급으로 노출.

- scheme `dup`(현 K3 carve-out — 서로 다른 handle 이 endpoint 공유)이
  이미 **capability 전달의 씨앗**.  최종 목표: dup/send 가 **partition
  rule 을 존중하는 capability 이동**으로 일반화.
- **capability-bound-allocation 연동**: partition-keyed zone 의 memory
  region capability 를 IPC 로 다른 partition 에 넘기려는 시도는
  **차단**(cross-tenant UAF 방지, capability 문서 I1).  즉 IPC 의
  capability 전달도 **partition invariant 를 위반하지 못한다** — 새
  cross-layer invariant(§7).
- **grant vs share**: memory region cap 을 넘길 때 소유권 이전(grant,
  sender 는 잃음) vs 공유(share, 양측 접근).  lease lifecycle 과
  연결 — lease 종료 시 bulk reclaim(capability §I4/I6)이 grant/share
  모두 회수.

## §4 zero-copy / caller-allocated — C1 독립성의 근거

messages are **caller-allocated**(LWKT 패턴) → IPC 는 alloc 을
호출하지 않는다.  이것이 **C1(ipc/alloc 독립)의 구조적 근거** — 우연이
아니라 설계로 강제.

- **작은 제어 message**: scheme buffer 로 inline 복사(현 구현) — 정책
  데이터라 저빈도, 복사 비용 무시 가능.
- **큰 payload**: **shared memory region capability + descriptor 만
  msgport 로**.  seL4 IPC buffer(고정 크기) 에는 descriptor(cap +
  offset + len), 실제 데이터는 공유 페이지.  복사 0.
- WaveTensor 데이터 경로(tensor buffer)가 정확히 이 케이스 — 대용량
  텐서를 복사 없이 accelerator daemon 과 공유(§3 grant, lease 로 수명
  관리).

## §5 real-time / bounded (RT §2.1 정합)

- **모든 IPC 연산 bounded WCET**: msgport `send`/`wait`, scheme verb,
  §2.2(c) 의 FreeReq drain 모두 상한.
- **priority inheritance / ceiling**(roadmap stage 3, spec **M5**):
  낮은 우선순위 tenant 가 점유한 endpoint 가 높은 우선순위를 막는
  priority inversion 회피.  현재 per-endpoint priority high-water mark
  만 있음 → 실제 inheritance 구현이 최종 목표.
- **mixed-criticality**: seL4 MCS + lease criticality attr(RT 문서)와
  결합 — hard-RT tenant 의 IPC 는 예약(reservation)된 budget 상에서.

## §6 cross-platform (cross-platform 문서 §IPC "independent" 정합)

- IPC core = **arch-neutral Rust**.  §0.5 atomic-free 가 arch memory
  model 을 회피하므로 AArch64 weak / POWER weaker ordering 에 **재검증
  불요** — 이것이 cross-platform 표의 "independent" 의 실제 근거.
- 유일한 arch 의존 = seL4 syscall(register 규약, IPC buffer 레이아웃)
  → **`Sel4Backend` trait 뒤로 완전 격리**(현 구조 이미 이 형태).  포팅
  시 backend impl 만 교체, msgport/scheme 로직 불변.

## §7 verification — 최종 목표 (formal-first 정합)

현재 5 assume discharged(M5/SC4/M1/K2 constructive), 6개 잔여(M2/M3/
M4/SC2/K1/K3, trusted boundary).  최종 목표 = 전부 discharge + **본
문서가 새로 요구하는 cross-layer invariant 추가**:

- **F1 (FreeReq 는 alloc 무호출)** — C1 보존, §2.2(a).  IPC 가 alloc
  edge 를 만들지 않음을 타입/증명으로.
- **F2 (FreeReq 는 owner CPU 에서만 처리)** — M4(per-CPU disjoint)의
  확장.  cross-CPU free 가 §0.5 를 우회하지 않음.
- **F3 (cross-CPU free 후 메모리 보존)** — allocator 의 conservation
  invariant(I) 와 IPC 의 K1/K2 를 잇는 **alloc↔ipc cross-layer proof**.
  "B 가 보낸 free 는 정확히 한 번 A 의 freelist 로"(중복/유실 0).
- **F4 (capability 전달이 partition invariant 보존)** — §3, capability
  문서 I1 과의 cross-layer.

F3 가 핵심 — allocator 시리즈와 IPC 를 하나의 검증 대상으로 봉합하는
지점(K1 cross-layer consistency 의 구체화).

## §8 결정 / 미결 요약

**결정 방향(강)**:
- §0.5 atomic-free 를 IPC 로 확장 → **atomic-free composition** 명제
  (cross-CPU 협조의 유일 통로 = atomic-free IPC)
- cross-CPU free = msgport FreeReq 위임(§2.1), async 수용, deterministic
  > throughput(§2.3)
- capability 전달은 partition invariant 하위(§3, F4)
- zero-copy = shared region cap + descriptor, C1 은 caller-allocated 로
  구조적 강제(§4)

**미결(측정/설계 필요)**:
- §2.2(a) FreeReq 채널 구현형태(고정 inline 슬롯 vs per-CPU 예약 링) —
  **유력: bounded 전용 채널**
- §2.2(b) back-pressure 정책(거부 vs local defer) — **유력: local defer**
- §2.2(c) drain 시점·상한(context switch / wait 경계 / quantum)
- §3 grant vs share 기본값, lease 회수와의 정확한 결합
- M5 priority inheritance vs ceiling 구현 선택(roadmap stage 3)

**⏳ 선행 의존**:
- 실제 `Sel4Backend`(roadmap stage 1) — kernel/ 에서 cap invocation
- F3 cross-layer proof 는 alloc 최종 구현(§2.1 FreeReq)과 동시 필요
