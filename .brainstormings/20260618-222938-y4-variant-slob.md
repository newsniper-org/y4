# Y4-variant SLOB

## 0. 발제 (사용자 2026-06-18)

> pluggable 문서의 "embedded SLOB-style front 가 작은 slab + index
> freelist" 를 보고 — SLOB 도 Linux 식 그대로가 아니라 Y4 맞춤 변형
> 이어야 하지 않을까?

정확.  앞선 패턴과 동형 — DragonFly SLAB 을 atomic-free SLUB-style 로
변형했듯 (improvements.md), Linux SLOB 도 그대로면 Y4 원칙 (§0.5 atomic-
free / pluggable contract C1~C4 / formal-first / hardening / capability)
과 충돌.  특히 **Linux SLOB 의 `slob_lock` = global spinlock → §0.5
즉시 위배**.

단 SLOB 만의 **새 긴장**: SLOB 의 정체성 = *메모리 overhead 극소*
(embedded < 수 MB RAM 용).  그런데 Y4 원칙 (out-of-band metadata,
hardening) 은 메타/overhead 를 늘림.  embedded 는 메모리가 가장 귀함 →
이 긴장 해소가 핵심 (§4).

## 1. Linux SLOB 현황 (= 변형의 baseline)

**SLOB = Simple List Of Blocks** (K&R-style, v6.4 제거 — SLUB 이
use case 흡수):

| 요소 | Linux SLOB |
|---|---|
| 목적 | 극소 메모리 (embedded, < 수 MB) — 메모리 overhead 최소화 |
| free list | 3개 (`free_slob_small` < 256B / `medium` < 1024B / `large`), page 단위 (`slob_page`) |
| 검색 | **first-fit** (page 내 block 순회) — O(n) |
| metadata | **in-band** — block 안에 `slobidx_t` (size + next offset) 임베드.  메타 극소 |
| size class | **없음** — 정확 크기 carve → internal fragmentation ≈ 0 (external 은 있음) |
| free | 인접 block **coalescing** (병합) — fragmentation 관리 |
| 동기화 | **global `slob_lock` (spinlock)** — 단순.  SMP scalability 나쁨 (embedded 는 보통 UP/소수 코어라 감수) |
| bigalloc | page 이상 → 직접 page allocator |

**SLOB 의 강점** (지켜야 할 정체성): 메모리 overhead 극소 (size class
없는 정확 carve + 최소 메타), 단순.
**SLOB 의 약점** (Linux 가 deprecate 한 이유): 느림 (first-fit O(n) +
coalescing), global lock, SMP 나쁨.

## 2. Linux SLOB 의 Y4 부적합 지점

| Linux SLOB | Y4 원칙 위배 | 출처 |
|---|---|---|
| **global `slob_lock`** | §0.5 atomic-free (+ deterministic) | improvements §0.5 |
| **in-band block header** | §2.2 out-of-band (+ 보안: overflow→header 오염) | pluggable C3/C4 |
| **first-fit O(n) 검색** | deterministic latency (worst-case 비결정) | improvements §2.5 |
| **free-time coalescing** | deterministic (비결정 latency) + Verus 난 (병합 invariant 복잡) | improvements §2.4/2.5 |
| **hardening 0** | pluggable C3 최소 hardening | pluggable C3 |
| **size-class-less** | pluggable 의 AllocFrontend/Freelist 가 size-class 가정 → trait 정합? | pluggable §2.1 |

## 3. Y4-variant SLOB 설계

### 3.1 지킬 것 — SLOB 정체성 (메모리 극소)
- **size-class-less 정확 carve** 유지 — internal fragmentation ≈ 0.
  embedded 의 메모리 극소 목적의 핵심.  (reference SLUB-style 의 size
  class 와 대비되는 SLOB 의 존재 이유)
- **단순성** — embedded 는 코드 크기도 제약.  과한 기교 X.

### 3.2 atomic-free (global lock → per-CPU, §0.5)
- Linux `slob_lock` (global spinlock) **제거** → per-CPU exclusive +
  critical section (§0.5).
- embedded 는 보통 UP / dual-core → per-CPU 부담 작음 (오히려 global
  lock 보다 단순할 수 있음).
- cross-CPU free = IPC 위임 (improvements §2.1) — embedded 에서 cross-
  CPU 자체가 드묾.

### 3.3 metadata — in-band ↔ out-of-band 의 embedded 긴장 (★ 핵심)
- Linux SLOB 의 in-band block header (size+next) = 메타 극소지만 보안 X
  (overflow→header 오염) + §2.2 위배.
- **trade-off**: out-of-band descriptor 는 보안 ↑ 지만 embedded 메모리
  ↑.  SLOB 의 존재 이유 (메모리 극소) 와 정면 충돌.
- **옵션**:
  - (a) **out-of-band 강제** (다른 form-factor 와 동일) — 보안 일관성,
    단 embedded 메모리 ↑
  - (b) **in-band + obfuscation** — 메타 극소 유지 (SLOB 정체성) + free
    block 의 size/next 를 obfusc (overflow→조작 차단).  보안의 일부만
    (격리 X, 변조 탐지만)
  - (c) **compact out-of-band** — descriptor 를 최소화 (page 당 1 word
    수준의 free 비트맵 + page 외부 작은 table).  보안 + 메모리 절충
- **잠정**: embedded 의 메모리 제약이 진짜 빡세면 (b), 보안 우선이면
  (a)/(c).  pluggable §4 의 "C3 form-factor 별 차등" 미결과 직결 — 이게
  그 차등의 첫 구체 사례.

### 3.4 deterministic — first-fit O(n) → bounded (§2.5)
- Linux first-fit = O(n) worst-case (page 내 모든 block 순회) → 비결정.
- **옵션**:
  - **bounded-fit** — 최대 k block 만 검색, 못 찾으면 새 page (worst-
    case O(k) 상한).  fragmentation 약간 ↑ 대신 deterministic
  - **segregated free list** — size 구간별 list (Linux 의 3-list 를 더
    잘게) → 검색 범위 축소.  단 size-class-less 정체성과 긴장 (구간이
    곧 coarse size class)
- **잠정**: bounded-fit 가 SLOB 의 size-class-less + deterministic 둘 다
  지킴.  k 는 측정 (improvements §2.9 측정 게이트 패턴).

### 3.5 coalescing — free-time → bounded / deferred
- Linux SLOB 은 free 시 인접 block 병합 (즉시) — 비결정 + Verus 난.
- **옵션**:
  - **bounded coalescing** — free 시 인접 1~2 block 만 검사 (O(1) 상한)
  - **deferred coalescing** — 병합을 free hot-path 밖 (wave-aligned
    idle, improvements §2.5) 으로 미룸.  fragmentation 누적 vs latency
  - **no coalescing** — bounded-fit + 새 page 로 충분하면 병합 생략 (단
    external fragmentation ↑)
- **잠정**: deferred (improvements §2.5 의 wave-aligned drain 과 같은
  메커니즘 재사용) 또는 bounded.  Verus: 병합 invariant (인접 free
  block 의 merge 가 no-overlap 보존) constructive 필요.

### 3.6 contract 정합 — size-class-less 가 trait 와 맞나? (★ pluggable 연결)
- pluggable 의 `Freelist` trait 은 `pop()->Option<usize>` (slot **index**)
  — size class slot 가정.  SLOB 은 size-class-less (정확 byte carve) →
  slot index 개념이 안 맞음.
- **함의**: `Freelist` trait 이 두 종류를 수용해야:
  - **slotted** (SLUB-style) — 고정 size class slot, index 기반 (improvements
    §2.9 의 B/D/E)
  - **offset-based** (SLOB-style) — 가변 크기 block, offset/size 기반
- **옵션**:
  - (a) `Freelist` trait 을 일반화 — `pop(size)->Option<Region>` (size
    인자 + region 반환) 로 양쪽 수용.  slotted 는 size 무시, SLOB 은 사용
  - (b) **별도 trait** — `SlottedFreelist` vs `BlockFreelist` 분리.
    AllocFrontend 가 어느 쪽이든 받게
  - (c) SLOB 은 Freelist trait 안 씀 — AllocFrontend 의 free slot 관리를
    SLOB 이 자체 내장 (Freelist 분리 이득 포기)
- **잠정**: (a) 일반화가 깔끔 — `Freelist` 가 "free space 추적" 추상화
  로 충분히 일반적이면 slotted/offset 둘 다.  단 contract (FL1~FL3) 가
  양쪽에 well-defined 해야.  pluggable §2.1 의 freelist 분리 결정을 SLOB
  이 시험 — trait 일반성 검증 사례.

### 3.7 hardening 차등 (embedded C3 최소선)
- pluggable C3 = obfusc + double-free + zero-on-free 최소.  embedded 는
  메모리/코드 제약 → C3 일부 완화 허용?
- **옵션**: form-factor 별 C3 최소선 — embedded = obfusc + double-free
  (zero-on-free 는 옵션), server = full.  단 "약화 금지" (pluggable C3)
  와 충돌 → "form-factor 별 baseline 차등" 으로 재정의 필요.
- pluggable §4 미결 (C3 form-factor 차등) 의 첫 구체 사례.

## 4. 핵심 긴장 — 메모리 극소 ↔ Y4 원칙의 메타 비용

SLOB 의 존재 이유 = 메모리 overhead 극소.  Y4 원칙 (out-of-band
metadata §3.3, hardening §3.7, contract descriptor) = 메타 ↑.  embedded
는 메모리가 가장 귀함 → **정면 충돌**.

**화해 방향**:
- Y4-variant SLOB 은 **"메모리 극소 우선, 그 제약 안에서 최대한 Y4
  원칙"** — atomic-free (§3.2, 공짜) + deterministic (§3.4, 거의 공짜)
  + double-free (§3.7, 비트 1개) 는 메모리 비용 거의 0 이므로 무조건
  지킴.  out-of-band metadata (§3.3) + zero-on-free + 강한 hardening 은
  메모리 비용 ↑ → embedded 차등 (in-band+obfusc 또는 compact).
- 즉 Y4 원칙을 **메모리 비용 순으로 계층화**: 공짜(atomic-free /
  deterministic / double-free) = 필수, 비쌈(out-of-band / zero-on-free)
  = form-factor 차등.
- 이게 pluggable C3 의 "form-factor 별 최소선 차등" 을 **메모리 비용
  기준으로 원칙화** → SLOB 이 그 frame 의 시험대.

## 4.5 Linux SLUB_TINY 참고 — SLOB-variant vs SLUB-tiny-config 재고 (사용자 참고 2026-06-18)

Linux 6.2 (2023) 가 SLOB 을 deprecate 하며 **`CONFIG_SLUB_TINY`** 도입
— SLOB 의 **직접 대체재**.
- SLUB_TINY = SLUB 코드베이스 재사용 + 메모리 최적화 (per-CPU partial
  list 제거, 작은 메타, scalability 양보).  embedded 를 *별도 allocator
  (SLOB)* 가 아니라 *SLUB 의 config 변종* 으로 흡수.
- Linux 의 결론: embedded 를 위해 별도 코드 (SLOB) 유지보다 SLUB 통합 +
  tiny config 가 낫다 (코드 중복 제거 + SLUB 의 hardening/debug 재사용).

**Y4 함의 — 재고**:
- Y4 도 embedded 를 (a) SLOB-variant (본 문서, 별도 front-end) vs (b)
  reference atomic-free SLUB-style 의 **tiny config** (size class 수 ↓,
  slab 크기 ↓, partial list 깊이 ↓) 로 재고.
- **(b) SLUB-tiny-config 우위**:
  - pluggable contract (C1~C4) + Freelist trait 을 reference 가 이미
    만족 → tiny 는 그 *config 변종*, 새 front-end contract 증명 불필요
    (덧셈 검증 — pluggable 핵심 이득)
  - atomic-free SLUB-style 이 이미 reference → tiny 는 파라미터 조정만
  - SLUB 의 hardening (C3) + capability layer 재사용
- **(a) SLOB-variant 우위**:
  - size-class-less 정확 carve = internal fragmentation 0.  SLUB-tiny 는
    size class 라 internal frag 잔존
  - 극단적 메모리 제약 (수백 KB RAM) 에선 internal frag 0 이 결정적
- **결정 기준 (측정)**: embedded 메모리 budget
  - 수 MB RAM → (b) SLUB-tiny (검증/코드 재사용 우위, internal frag 감수)
  - 수백 KB RAM → (a) SLOB-variant (internal frag 0 필수)

**★ Y4 pluggable 이 Linux 딜레마를 무효화**: Linux 는 SLOB vs SLUB_TINY
**택1** (CONFIG, 코드 중복 때문에 SLOB 폐기).  Y4 는 **pluggable** 이라
(a)(b) **둘 다 AllocFrontend 구현체로 공존** — form-factor 가 메모리
budget 으로 선택.  게다가 Y4 는 contract 덧셈 검증 + Freelist trait
재사용으로 **중복 유지 비용이 낮음** (Linux 가 SLOB 버린 이유 = 코드
중복인데, Y4 는 그 비용이 작음) → 둘 다 들고 가도 부담 적음.

## 5. 결정 / 미결

### 방향 (잠정)
- Y4-variant SLOB = pluggable AllocFrontend 의 embedded 구현체
- 지킴: size-class-less 정확 carve (정체성) + atomic-free (§3.2) +
  bounded-fit deterministic (§3.4) + double-free (저비용 hardening)
- 차등: metadata (in-band+obfusc vs out-of-band) + 강한 hardening 은
  embedded 메모리 제약에 따라

### 미결
- **(★ §4.5) SLOB-variant vs SLUB-tiny-config** — embedded 를 별도
  SLOB front-end (본 문서) 로 갈지, reference SLUB-style 의 tiny config
  로 갈지.  Y4 는 pluggable 이라 둘 다 가능 → form-factor 메모리 budget
  (수백 KB = SLOB / 수 MB = SLUB-tiny) 측정 후.  본 SLOB 발제의 존재
  의의 자체가 이 측정에 달림
- **§3.3 metadata** — in-band+obfusc (b) vs compact out-of-band (c) vs
  강제 out-of-band (a).  embedded 실제 메모리 budget 측정 후
- **§3.6 Freelist trait 일반성** — slotted + offset-based 를 한 trait
  으로 (a) vs 분리 (b).  pluggable §2.1 결정을 SLOB 이 시험 → trait
  설계로 피드백
- **§3.4/3.5 bounded-fit k + coalescing 정책** — 측정 (improvements §2.9
  게이트 패턴)
- **§4 form-factor 차등의 원칙화** — "메모리 비용 순 계층화" 를 pluggable
  C3 의 정식 규약으로 승격할지
