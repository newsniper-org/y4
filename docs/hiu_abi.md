# Y4 ↔ HIU ABI (v1.0-rc1 — 동결 후보 · WaveTensor `e88f6f4` · 양측 sign-off 대기)

이 문서는 Y4 가 WaveTensor 가속기의 HIU(호스트 인터페이스)에 의존하는
**유일한 ABI 표면**, 즉 HIU 구성 표면(MMIO)의 **Y4 측 문서**다.
상대편은 WaveTensor 정본 `docs/wt64v1-architecture-guide/` 부록 E(E.1
레지스터 맵 · E.2 변환 항목 · E.3 미적중 채움 · E.6 완료 통지 · E.7 페이지
소유권 · E.9 마스크 키와 논스)와 §3.10 「호스트 ABI 경계」다.

- 용어와 정본 인용: [`./glossary.md`](./glossary.md) (§2–§10).
- 이 문서의 정본(`G/…:줄`) 인용은 따로 표시가 없으면 WaveTensor `e88f6f4`(v1.0 동결 후보 · 정본 트리
  `docs/wt64v1-architecture-guide` = `c105b273a87eabd2ceb3c1c19c3d32bc054bd296`) 기준이다. 축자 인용(「…」)은
  그 커밋의 문면과 글자 단위로 맞춘다(강조 표지는 뺀다). 현행 사실을 말하는 RTL 인용(`rtl/…:줄`)도 따로
  표시가 없으면 `e88f6f4` 기준이다 — RTL 은 ABI 출처가 아니므로 정본 인용이 있으면 정본이 먼저다.
- **예외 — 판 이력 블록**(아래 「> **v0.x → v0.y (날짜).**」 인용 블록 · §7 채널 기록 · §8 이력) 안의 인용은
  그 블록이 적은 sha 기준이다(표지 없는 것은 `645bed0`). 판 이력은 다시 쓰지 않고, 낡은 사실은 새 판 이력
  블록에 「해소」로 적는다.
- 이 문서가 동결(`v1.0 frozen`)되어야 Y4 의 mock-HIU(`hiu/mock/`)와 lease
  capability 런타임(Phase C)이 시작될 수 있다.

## 0. 동결 정책

- 동결은 **Y4 측 + WaveTensor 측 양쪽 합의**로만 일어난다. 정본 §3.10 은 「동결에는
  양쪽 합의가 필요하다 … 한쪽만 바꾸면 조용히 어긋난다」고 적는다
  (`G/chapters/03-hiu.typ:1610-1616`). Y4 는 일방 변경을 무효로 취급한다(Y4 정책).
- **판 워드는 `(major << 16) | minor` 로 한다**(정본 `03-hiu.typ:1650-1652`, §1.4).
- **minor / major 기준** (정본 3.10 「판의 뜻」 `03-hiu.typ:1650-1692` — Y4 의 행동 기준 문면 그대로):
  - minor 증가 = 같은 major 의 v1.0 적합 드라이버(§1.2.1 의무를 지키는 드라이버)가 낼
    수 있는 모든 접근 순서에서, 그 드라이버가 *의무대로 해석한 결과*와 v1.0 의 격리 ·
    fail-closed 성질이 그대로인 변경. 적합 드라이버의 접근 순서에서는 일어날 수 없는
    사건의 보고만 달라지는 변경도 minor 다. 그 밖은 major.
  - minor 의 예:
    - (a) 미배정 오프셋에 새 워드를 두되 reset 값이나 0 이 이전 동작을 재현하는 경우.
      정본의 「*레지스터 추가는 하위 호환 형태*가 된다」(`03-hiu.typ:813-816`)가 이것이다.
    - (b) 엄격 예약 비트를 수락으로 넓히되 0 이 v1.0 동작을 내는 경우. 또는 v1.0
      드라이버가 쓰지 않는 워드(E.1.3 「소비 회로가 없는 RW 워드」)를 수락으로 넓히는 경우.
    - (c) v1.0 에 없는 기능을 쓸 때만 나오는 새 완료 kind(`e-defined.typ:1082-1087`), 또는
      호스트가 무시하는 여백 필드(`:1141-1147`).
    - (d) FAULT_STATUS `[31:20]` 의 새 원천 비트(`03-hiu.typ:1666-1669` — `[19]` 는 v1.0 배정, §1.3). 단 v1.0 적합 드라이버의 접근 순서에서는
      서지 않는 원천 — v1.x 기능을 켤 때만 사는 원천이거나 v1.0 에서도 이미 정본 위반인
      사건 — 에 한한다. 적합 순서에서도 설 수 있는 원천은 major 다(v1.0 드라이버가 미지
      비트로 fail-closed 해 정상 운용을 잃는다). 기존 비트에 새 원천을 접는 것도 뜻 변경이라
      major 다. 정본은 「v1.0 에서도 이미 정본 위반인 사건」을 E.1.1 「호스트 해석 규범」 「4항이 적합
      드라이버에게서 뺀 기입」으로 가리킨다. 겹치는 LBID 슬롯 구간을 지목하는 구성도 그 목록에 든다(정본 E.1.1 4항 귀결
      `e-defined.typ:208` — 「유효한 두 LBID 엔트리가 겹치는 슬롯 구간을 지목하는 구성을 쓰지
      않는다」, §2.8).
    - (e) `0xC00` 구역 `+0x0C` VPN 상위를 수락으로 여는 VA 확장(§1.3 변환). **요청 쪽 조건**(정본
      `03-hiu.typ:1678`): 넓은 VA 요청의 생성은 호스트가 새 RW 필드(reset 값 0 = v1.0 VA 범위)로
      켤 때만 일어나고, 끈 상태의 장치는 VPN 상위 비0 요청을 만들지 않는다. v1.0 드라이버가 `0xE0C` ≠ 0
      정지를 볼 수 있는 확장은 major 다 — 그 정지를 풀 VPN_HI 기입이 v1.0 에서 거절돼 드레인이 끝나지
      않는다(Y4 는 그 장치를 격리한다). 끈 상태의 위반을 알리는 비트가 필요하면 그 판이 `[31:20]` 에 연다.
    - (f) RW 워드에 reset 값 · 0 이 v1.0 동작인 RW 필드, 또는 쓰기 무시 RO 필드를 더하는 경우.
      RW 워드에 더할 수 있는 것은 이 둘뿐이다(정본 E.1.1 일반 규범 `e-defined.typ:208` · 3.10
      `03-hiu.typ:1679-1682` — 같은 문장).
  - 언제나 major: 기존 필드의 위치 · 폭 · 뜻 변경 · 새 필수 호스트 단계 · 0/reset 값이
    v1.0 과 다른 새 필드 · v1.0 적합 드라이버가 낼 수 있는 접근에서의 수락 → 거절 ·
    비트 제거 · `MASK_STATUS` `[8]`/`[9]` 의 뜻 변경 · 변환 항목 표면 배치 변경.
  - 판의 일이 아닌 것: 변환 저장의 형상(파티션당 용량 · 연관도 · 교체 정책) 변경
    (§1.3 변환 결과 규범 (g) · (h)). *예외* — 동시에 정지할 수 있는 조회 지점이 여럿인 형상을 들이는
    개정은 판의 일이다: minor 기준의 판정을 받는다(정본 `03-hiu.typ:1689`).
  - 판 보고: minor 는 누적이다. 적합성을 되돌리는 RTL 수정은 번호를 바꾸지 않는다.
- **비0 판 값은 양측 sign-off 뒤 별도 커밋에서만 장치에 들어간다**(합의 2026-10-09 — RTL 에는 이미 `require(Ident.PRE_AGREEMENT == 0, …)` 게이트가 있다, `rtl/…/top/Wt64Top.scala:1821`).
  순서: 사용자 확정 → 정본 spec 커밋(Y4 가 diff 대조) → WaveTensor 선-formal · RTL ·
  후-formal 파도(이 동안 `0xFFC` = 0) → 이 문서 `v1.0 frozen` + 양측 sign-off → 판 값
  `0x0001_0000` 커밋. 파도에서 정본 문면 수정이 나오면 1–2 단계(사용자 확정 · 정본 spec 커밋)로 돌아간다.
  파도는 W0–W4 로 끝났고 정본 규범 수정은 나오지 않았다(2026-10-16) — 지금은 `v1.0 frozen` + sign-off 단계다.
- v0.x · v1.0-rc 는 동결 전이다. 누구든 바꿀 수 있지만 커밋 메시지에 `hiu-abi: <요지>` 접두가 필수다.
- 정본 자신은 pre-stable 이고 `T_stable` 이 미정이다(`G/chapters/00-preface.typ:36-54`).
  이 문서는 정본 변경을 따라간다.

> **현재 상태:** v1.0-rc1 — 동결 후보 (WaveTensor `e88f6f4`, 양측 sign-off 대기). 정본 spec 커밋 `6a25359` ·
> 정정 `8af46df` · 명확화 `b81df18` 과 RTL 파도 W0–W4 착지(`e88f6f4`) 대조 완료(2026-10-16) — Y4 가 정본에 요청할
> 것은 남지 않았다(v1.x 비차단 명확화 제안 하나 — §2.4 3). 남은 것: WT 의 history 보존 약속 · 이 문서 `v1.0 frozen`
> + 양측 sign-off · 판 값 커밋. `0xFFC` 장치 값 = 0(판 0, §1.4).

## 1. 구성 표면 (호스트가 보는 4 KiB 페이지)

구성 표면은 **4 KiB 한 페이지**의 32-bit 워드 맵이다. 페이지를 호스트 버스(PCIe BAR
등)의 어디에 두는지, 워드의 바이트 순서를 버스에 어떻게 싣는지는 보드·어댑터 층의
일이며 이 ABI 가 정하지 않는다(P3, `docs/hw_mechanism_abstraction.md`; 정본도 구성
표면의 바이트 순서를 정하지 않는다).

**한 페이지는 쪼갤 수 없다** — 게스트에게 어느 구역이든 직접 MMIO 를 주면 같은
페이지의 변환·마스킹 구역도 함께 닿는다. 그래서 **게스트는 이 페이지에 직접 닿지
않고, 모든 구역을 Y4 가 capability 검증 뒤 대행한다**(Y4 정책 — 아래 「Y4 사용」
열의 분류도 Y4 의 선택이다).

#### 1.2.1 v1.0 드라이버 의무 (§0 minor 기준의 전제)

WaveTensor 가 Y4 의 의무 목록을 셋으로 나눠 받았고, (A) 는 정본에 착지했다.

**(A) 정본 E.1.1 「호스트 해석 규범」** (`e-defined.typ:208` — 장치 계약의 짝, 넷을 지키는
드라이버가 *v1.0 적합 드라이버*):
1. 미배정 오프셋에 쓰지 않는다(3.7 「레지스터 추가는 하위 호환」의 전제).
2. RO 읽기는 정의된 비트로 마스크해서 해석한다(완료 디스크립터 「*호스트는 예약을 무시한다.*」의
   MMIO 판). 모르는 fault 비트의 처리는 정본이 호스트 정책으로 남긴다 — Y4 는 fail-closed 다((C)).
3. RW 구성 워드의 *쓰기 가능 필드*는 읽고-고치고-쓰기(RMW)로 갱신한다. **바꾸려는 필드 밖의 비트는
   되읽은 값 그대로 되쓴다** — RO 필드는 쓰기 무시이므로 되써도 무해하다. 예약 비트는 RO 필드가
   아니고 v1.0 에서 읽기 0 이라 되써도 0 이다.
4. 거절 + `[6]` 을 기능 탐침으로 쓰지 않는다. 귀결: v1.0 이 워드의 내용 · 자리로 거절하는 기입을
   내지 않는다 — WO · 발화 워드와 RW 워드의 예약 비트에 0 을 쓰고, E.1.3 소비 회로 없는 RW 워드(링
   base 넷 · `SQ_SIZE` · `SQ_TAIL`)와 `0xC00` 예약-엄격 워드에 쓰지 않는다. 또 유효한 두 LBID
   엔트리가 겹치는 슬롯 구간을 지목하는 구성을 쓰지 않는다 — v1.0 장치는 그것을 판정하지 않고
   수락하므로 비겹침은 이 의무가 진다(`8af46df` 에서 더해짐, Y4 쪽 §2.8). `0xE14` 의 드레인 판정
   거절은 시점의 거절이라 여기 들지 않는다.
- Y4 는 v1.0 에서 `CQ_SIZE` 도 쓰지 않는다 — 같은 값 기입은 장치 무동작이지만 `CQ_SIZE` 는 3.7.2
  전역 구성이다(§2.7).

**(B) 3.7.2 결속 전환 절차:** `0xE14` 기입 뒤 되읽기(결속 · A · D)를 확인한 뒤에만 재개한다(§2.4).

**(C) Y4 정책 (장치 정합성에는 필요 없음):**
- `0xE14` 기입은 RMW 꼴이다 — 되읽은 값의 `[31:8]` 을 그대로 두고 `[7:0]` 만 바꿔 쓴다((A) 3 —
  `[9:8]` 은 쓰기 무시, `[31:10]` 은 읽기 0). v0.3 의 「`[7:0]` 만 · 상위 0」은 장치 결과는 같지만
  (A) 3 의 글자에 맞지 않아 바꿨다.
- **구성 페이지 접근은 모두 자연 정렬 32b 전폭 load/store 이고, 되읽기도 정렬 주소로 한다.** 비정렬
  쓰기(`0xE14` 에서는 `0xE15`–`0xE17`)는 장치가 거절 + `[6]` 하고 A · D · 결속을 움직이지 않으며, 비정렬
  읽기는 0 · fault 없음이다(`e-defined.typ:332` 3항 · `03-hiu.typ:874`). 정렬 주소의 부분 바이트(바이트
  인에이블) 쓰기가 장치 포트에 닿지 않게 하는 것은 어댑터 몫이다 — 정본 경계 밖이고 미측정이다
  (`e-defined.typ:332` 3항 · 3.9 `03-hiu.typ:1549`). 그래서 Y4 는 그것을 플랫폼 레지스트리 전제
  (`hw_mechanism_abstraction.md` §2 — 구성 페이지 UC · 비 write-combining · 32b 접근을 쪼개거나 합치지 않음)로
  둔다. Verus MMIO 접근자의 사전조건은 `off % 4 == 0` 이다(코드는 `hiu/` 착수 때).
- `0xF84` FAULT_CLEAR 에는 *처분을 마친* 비트만 쓴다 — 읽은 값 가운데 §1.3 FAULT 표로 처분한
  비트. 모르는 FAULT 비트는 fail-closed 로 처리한 뒤 해제한다(고정 마스크를 쓰지 않는다).
  `[12]` 는 §2.6 귀속을 마치기 전에는 해제하지 않는다.
- 매 `MASK_REKEY` 전에 그 파티션의 키와 논스를 새로 기입한다.
- `0xE0C` MISS_VPN_HI 가 0 이 아닌 미적중은 fail-closed 로 처리한다(v1.0 은 VA 44b 만 사상).
  v1.0 에서 Y4 는 VPN_HI(`+0x0C`)를 쓰지 않는다 — 수락된 VPN 기입이 0 으로 되돌리고, 수락된 VPN_HI
  기입은 FRAME 유효를 내린다.
- 정지한 파티션에는 `0xE04[0]` = 1 인 동안 `0xE08` 이 보고한 VPN 만 커밋한다(§2.2).
- 데이터 필드가 불량한 COMMIT(FRAME 유효 없는 V=1 · `[27:0]` 비0)을 내지 않는다(Verus 사전조건).
- V=0 COMMIT 은 `0x0000_0000` 으로 쓴다. 장치는 V=0 COMMIT 의 `[30:28]` 을 수락한다 — 정의된 필드이고 예약은
  `[27:0]` 뿐이며, V=0 항목은 적중하지 않아 그 값은 관측되지 않는다(`e-defined.typ:308` · `:311` · WT DP-20).
- LBID 사상표 대행 기입은 §2.8 검사를 통과한 것만 쓴다(Verus 사전조건 `lbid_write_ok`).

### 1.3 Y4 가 쓰는 워드

**페이지 소유권** (정본 — E.1.2 `e-defined.typ:222-233`; 규범은 E.7 `:1370–`) — 상태는
호스트 소유 / 장치 소유 둘뿐이다.

| 오프셋 | 이름 | 접근 | 뜻 |
|---|---|:-:|---|
| `0x200` | OWN_IDX | RW | 조회 대상 페이지 프레임 |
| `0x204` | OWN_STATUS | RO | `[0]` 1 = 장치 소유 |
| `0x208` | OWN_SET | WO | 장치로 이양할 프레임 — 기입이 곧 전이 |
| `0x20C` | OWN_CLR | WO | 호스트로 회수할 프레임 — 기입이 곧 전이 |

**완료 방향 (E.6)** (정본, `0x32C` 만 v1.x 합의) — 통지는 **완료 링 항목이 유일한 수단**이다.

| 오프셋 | 이름 | 접근 | 비고 |
|---|---|:-:|---|
| `0x300`/`0x304` | CQ_BASE_LO/HI | RW | 오늘 완료 링은 장치 상주. 쓰기는 거절 + `[6]` (§1.2) |

  미친다 — 그 전에 판정이 래치된 요청은 래치된 판정으로 끝까지 간다(정본 `e-defined.typ:310` — 3.6.2
  판정 래치).
- (b) **V=0 커밋 뒤 같은 (파티션, VPN) 조회는 반드시 미적중이다.** 그 VPN 이 상주하지 않았으면
  그 (파티션, VPN) 에 관해서는 조회 결과가 바뀌지 않는다. 같은 파티션의 다른 항목은 (h) 의
  COMMIT 축출로 밀려날 수 있다(합의 — 직접 사상에서 V=0 는 그 색인 칸을 무조건 덮는다,
  `rtl/…/hiu/XlateStore.scala:225-231`).
  - **철회 효력 범위** (정본 3.7.2 「철회의 효력 범위」 `03-hiu.typ:1322-1334`): V=0 COMMIT 과
    flush 는 커밋 에지 *뒤에 판정되는* 조회에만 효력이 있다. 판정된 요청은 셋 — 조회 지점에 판정이
    래치된 요청 · 그 뒤 단계(마스킹 · 실행 · 승인)의 요청 · 메모리 파이프 착지 뒤에는 승인 뒤
    소비분이다. **완전한 철회 = V=0 · flush + 그 에지 뒤의 드레인 관측.** 승인 뒤 소비분까지 드레인
    정의역이 덮는 것은 메모리 파이프 착지의 B.5 선행 조건이다. Y4 의 귀결은 §2.7.
- (c) 축출은 같은 파티션 안에서만 일어난다(3.6.1 결과 3, `03-hiu.typ:598-600`).
- (d) 미적중 정지는 정지한 요청의 (파티션, VPN) 에 대한 V=1 커밋(거부 채움 포함)이 수락되면
  풀린다. **각 요청의 판정(적중 · 프레임 · 권한)은 조회 지점에서 처음 적중한 사이클에 정해지고,
  요청이 조회 지점을 떠날 때까지 유지된다 — 그 뒤의 커밋 · flush 는 그 요청의 판정을 바꾸지
  않는다**(정본 3.6.2 「판정 시점과 판정 래치 — 신설」 `03-hiu.typ:729-737`). 래치된 판정은

    HIU-4(`XlateSurface.Inv_AtMostOneValidPerVpn` — 칸 1 cfg 에서 공허하고, 반증력은 칸 2 cfg 둘 ·
    `del_commit_replaces_vpn` · `pair_host_index` 가 진다)는 *모델 위* 증명(선-formal TLC — RTL 이 아니다)이고,
    RTL 쪽은 `XlateDoor/door.sby` bmc 깊이 16 *유계*뿐이다(무계 미수렴). `b81df18`–`f67e3d6` 사이 HIU-4 는
    미착수였다(옛 `XlateStore.tla` `Inv_AtMostOneCandidate` 는 항진 — 범례 `d-properties.typ:17`). HIU-5 · HIU-6 은
    부분 증명이다(합성 서술). Y4 는 이 축들을 RTL 증명으로 읽지 않고 결과 규범 (a)–(h) 에만 기댄다.
- (e) `0xE00` flush 는 그 파티션의 항목을 전부 무효로 한다.
- (f) 스테이징은 장치에 하나다. 열은 VPN → FRAME → COMMIT 이다.
  - VPN 기입은 기입 주소의 파티션을 래치하고 FRAME 스테이징의 유효를 내린다. VPN 재기입은
    래치를 덮고 FRAME 유효를 내리며, FRAME 재기입은 덮는다(합의 — 규범으로 올린다).
  - VPN 유효가 없을 때(reset 뒤 · flush 뒤)의 FRAME 기입은 거절 + `[6]` · 무효과다(합의).
  - FRAME 은 래치 파티션과 같은 기저에서만 수락한다(다르면 거절 + `[6]` · 스테이징 불변).
  - V=1 COMMIT 은 **FRAME 유효**를 요구한다 — 마지막 VPN · VPN_HI 기입 뒤에 수락된 FRAME 이 있을
    때만 선다. V=0 COMMIT 은 VPN 유효만 요구한다(프레임 무관)(정본 `e-defined.typ:311`).
  - 거절 사유와 그 시점(정본 `e-defined.typ:308`):
    - 주소 · 스테이징 상태로 판정되는 사유(래치와 다른 파티션 기저 · VPN 없음 · 없는 파티션 기저)는
      곧장 거절 + `[6]` 이다.
    - 데이터 필드 사유(FRAME 유효 없는 V=1 · `[27:0]` 비0)는 수락 사이클에 거절한다 — 그 수락은
      아래 유계 정지 뒤일 수 있다(MMIO ready 의 조합 입력에 wdata 를 두지 않는 구조 규율 때문).
      재구현의 정지가 실제 1 사이클이라는 것은 3.9 의 구조 논증이다(미측정 — `03-hiu.typ:1552`). 거절은
      원천별 sticky 를 거쳐 `[6]` 에 합류한다(같은 줄).
    - 어느 경우든 거절된 기입은 아무것도 움직이지 않는다.
  - 커밋은 스테이징을 소진하지 않는다 — 같은 짝의 재커밋과 V=0 되풀이는 매번 커밋된다.
    없는 파티션 기저로의 기입은 거절 + `[6]` 이고 스테이징을 움직이지 않는다
    (`e-defined.typ:423-425`). 래치 파티션의 수락된 flush 가 두 스테이징 유효를 내린다.
  - 하류 슬롯이 찬 동안의 *적법한* COMMIT 은 버스를 정지시킨다. 정지 중에는 효과가 없고,
    슬롯이 비면 같은 기입이 수락되어 단일 에지로 커밋된다 — 거절도 드롭도 아니다. 정지는
    장치 의무로서 유계 시간 안에 풀리고, 호스트 조치에 기대지 않으며 다른 정지(미적중 정지 ·
    부팅 소거 구간)와도 독립이다(정본 `e-defined.typ:308`). 재구현의 측정(3.9 `03-hiu.typ:1552` · WT DP-21 ·

    설치가 오지 않는 동안 정지 ≤ `xlateParts` 사이클(참조 형상 4)을 문 + 저장 합성 태스크
    `XlateDoor/door.sby` `prove_stall`(abc pdr 무계)과 저장 블록 쪽 `xlatestore.sby` `s_pend_bounded` 가 재고,
    조립층 `assembly.sby` 는 조립 절반(정지 중 무효과 `a_xhold_quiet` · ready 원천 `a_ready_only_slot`)과 문
    결선 복제와 실물의 같음(`a_door_*`)을 잰다. 실제 1 사이클은 구조 논증이고(단언 상수 `F_N` = `xlateParts`
    는 느슨하다) 규범은 사이클 수를 걸지 않는다 — Y4 는 유계성과 호스트 조치 독립에만 기대고 절대 사이클
    수를 ABI 로 삼지 않는다. 단일 접근의 정지는 Y4 의 폴링 타임아웃이 다룰 수 있는 대기가 아니다.
- (g) 파티션당 용량 · 연관도 · 교체 정책은 형상이고 장치 안쪽의 일이다. `0xFF8` HIU_SHAPE 가
  용량(칸 수)을 *정보로* 알린다(§1.4). 정합성은 용량에 기대지 않는다. 교체 결정과 교체 상태
  갱신은 커밋 경로에서만 일어나고, 조회는 저장과 교체 상태를 쓰지 않는다(5.3 상태열 동일성

  경로에 정지나 ready 를 만들지 않는다. 교체 상태는 파티션별이고 다른 파티션의 상태에 기대지
  않는다.
- (h) **진행 보장** — 축출은 같은 파티션에 대한 호스트 COMMIT(V=0 포함)과 flush 의 결과로만
  일어난다. 시간 경과 · 조회 · 다른 파티션 활동 · 배경 작업에 의한 자발 축출은 없다. 그래서
  (d) 와 함께 드라이버는 미적중 채움으로 언제나 수렴한다. 이 보장은 용량 · 연관도와 무관해야
  하고, 동시에 정지할 수 있는 조회 지점이 여럿인 형상은 그것을 구조로 지켜야 한다. 그런 형상은
  `0xE04`–`0xE0C` 관측면이 한 요청을 골라 그 정지가 풀릴 때까지 바꾸지 않아야 한다. v1.0 관측면 문면은
  단일 조회 지점을 전제한다(정지 지점이 하나라는 것은 E.4 3항). 그 형상을 들이는 개정이 지킬 것 —
  `0xE04[0]` = 1 ⇔ 어느 조회 지점이든 정지 중 · 관측된 한 요청의 `[15:8]` · `0xE08` · `0xE0C` 는 그 요청을
  푸는 V=1 COMMIT 말고는 바뀌지 않음 · 판정 래치는 조회 지점마다 선다 — 과 그 개정이 minor 기준의
  판정을 받는다는 것(정본 `e-defined.typ:312` · `03-hiu.typ:1689`). Y4 의 미적중 루프(§2.2 4)가
  여기에 기댄다.

| `[13]` | 재키잉 중 입력 기입 | ⑶ 부터 유계 재시도 |
| `[15]` | step 프로그램 불량 | 그 임대에 보고 |
| `[17]` | 엔트로피원 건강성 | `lease_capability.md` I5 (오늘 상수 0) |
| 그 밖 · 모르는 비트 | | 게스트 정책으로 넘기거나 fail-closed (§1.2.1) |

### 1.4 장치 식별 — `0xFFC` 판 · `0xFF8` 형상

**`0xFFC` HIU_ABI_VERSION (RO, 정본)**
- **합의 전 값은 0 이다. 판 0 은 물려받은 `0x000`–`0x11F` 에 어떤 레이아웃도
  약속하지 않는다**(`03-hiu.typ:1630-1638`, `e-defined.typ:504-505`; HP-2).
- 분할 `[31:16]` major · `[15:0]` minor, v1.0 = `0x0001_0000`(정본 `03-hiu.typ:1650-1652` · `e-defined.typ:505`).
  major 변경 = 비호환. 비0 값은 sign-off 뒤 별도 커밋에서만 들어간다(§0).
- Y4 는 major == 1 에만 결속한다. 판 0 이나 다른 major 이면 진행하지 않는다. 기능 x 는
  minor ≥ x 일 때만 쓴다.

**`0xFF8` HIU_SHAPE (RO — 정본 `e-defined.typ:503`, RTL 착지 W1 `9b6eee6`)**
- `[7:0]` 실재 파티션 수 · `[23:8]` 파티션당 항목 용량 = 파티션당 저장 칸 수(파티션마다 다르면
  최솟값) · `[31:24]` RO 예약 = 0. 두 필드 모두 개수 인코딩이다. (WT 첫 제안 `[15:8]` 색인 수를 Y4 가
  형상 비노출 표면에 맞춰 바꿨다.)
- **용량 = 파티션당 저장 칸 수 — 임의 VPN 집합의 동시 상주는 보장하지 않는다**(합의 — 결과
  규범 (g)). 직접 사상의 16 은 칸 수이지 「임의 VPN 16 개 동시 상주」가 아니다(하위 비트가 같은
  VPN 끼리 서로 축출한다).
- 읽기 순서: `0xFFC` → `0xFF8`. Y4 는 major 1 일 때만 `0xFF8` 을 해석한다.
  - `[7:0]` = 0 은 「표면 없음」이다. W1 뒤의 판 0 장치도 `0xFF8` 값을 낸다(참조 형상 파티션 4 × 칸 16 에서
    `0x0000_1004` — 3.9 `03-hiu.typ:1556`). Y4 는 판 0 에서 진행하지 않으므로 그 값을 해석하지 않는다.
  - `[7:0]` 이 1–4 밖이면 장치 결함으로 보고 fail-closed.
  - 용량은 *정보*다 — 사전 채움 양과 성능 계측에만 쓰고 정합성 판단에는 쓰지 않는다. 사전
    채움은 힌트이고 정합성은 결과 규범 (d) · (h) 에 기댄다. 0 이면 fail-closed.
- 쓰기는 거절 + `[6]` 이다(RO). 폭과 스테이징 수는 필드에 넣지 않는다(합의).

## 2. 시간 계약 · 순서 계약

### 2.1 요청 경로 — 상수 시간은 「경로 간 동일성」

- 요청은 여섯 단계를 지난다: 접수 → 고정 지연 → 변환표 조회 → 물리 주소 마스킹 →
  요청 실행 → 접근 승인. 적중 · 대체 · 미적중이 **같은 상태열**을 지난다
  (`03-hiu.typ:62-74`, `05-security.typ:230-232`).
- **절대 사이클 수는 ABI 가 아니다** (`05-security.typ:250-253`; H4-1). Y4 는 사이클
  수에 기대는 timed-read 를 쓰지 않는다.
- **요청의 발신자는 PE 쪽이다**(H4-6). **호스트 발행 DMA 단발 표면은 이 ABI 에 없다**
  (G4). Y4 의 데이터 경로는 페이지 소유권 이양(§1.3)과 링(E.5/E.6) 위에 선다.
- **요청 → 파티션 결속**은 `0xE14` ACTIVE_PART 가 정한다(정본 `e-defined.typ:329` · `:332`, §2.4). 패브릭의 일은 한 순간에
  한 임대(= ACTIVE_PART)의 것이다(`b-gaps.typ:1190-1192`). 재구현에서 HIU 요청 파티션의 유일한 구동은 결속
  레지스터다 — 최상위 요청 파티션 입력 `hiuReq.part` 는 W4 `e88f6f4` 에서 은퇴했고, 응답의 파티션 출력은 결속의
  메아리로 남는다(3.9 `03-hiu.typ:1556`).
- 마스킹 재키잉은 요청 경로 밖의 구성 사건이다(사이클 수는 ABI 아님).

### 2.2 미적중 채움 (E.3, HP-6)

1. 미적중은 **오류가 아니다**. 조회 단 전체가 배압으로 정지하고, `0xE04[1]` sticky 가
   선다. 이것은 FAULT_STATUS 에 접히지 않는다.
2. Y4 는 `0xE04` · `0xE08`/`0xE0C` 를 읽는다. 값은 정지 게이트 스냅샷이고, 읽어도
   아무것도 해제되지 않는다. 채움 파티션은 `0xE04[15:8]` 이 알린다.
3. Y4 가 그 파티션 창에 **`0xE08` 이 보고한 VPN 만** 커밋한다(VPN → FRAME → COMMIT, §1.3 — v1.0
   에서 VPN_HI 는 쓰지 않는다). **정지를 푸는 것은 그 VPN 의 V=1 커밋뿐이다**(결과 (d)).
4. 정지는 채움 직후 다시 설 수 있다(파이프 안의 다음 요청이 미적중이면 둘째 정지).
   그래서 Y4 는 `[1]` 이 아니라 `[0]` 을 보고 루프를 돈다.
5. 루프가 끝난 뒤 `0xE10` 으로 sticky 를 한 번 해제한다. **순서는 「항목 기입 → 해제」**
   다. 정지 중에 쓴 해제는 유실된다(fault 도 효과도 없음).

- **거부 채움:** 사상이 없는 VPN 의 정지는 V=1 · R=W=X=0 커밋으로 푼다 → 적중 → 승인
  거부 + `[4]`. 정리는 드레인 종류에 따라 다르다.
  - 임대 *회수*(회전 ⑴)의 드레인: ⑵ flush 와 짝짓는다.
  - 스케줄 *전환*(§2.4)의 드레인: 그 VPN 들의 V=0 무효화를 `DRAIN_ALLZERO` 관측 뒤, 재개
    전에 한 번에 한다. 루프 안에서 바로 무효화하면 아직 판정되지 않은 같은 VPN 요청(뒤의
    단 · 이후 투입)이 다시 정지할 수 있다. 파티션 flush 는 하지 않는다. 거부 VPN 의 V=0 가 같은
    색인의 살아 있는 항목을 밀어낼 수 있으나 정합성과 무관하다(미적중 재채움 — 결과 (b)).
  - 거부 채움이 드레인을 완주시키는 근거(합의 — 범위 한정): 승인 거부된 요청은 승인과 같은
    사이클에 `valid=1 · granted=0 · 값 0` 으로 정의역 ① 을 떠나고 `[4]` 를 세운다. ⑥ 순서
    토큰은 HIU 경로와 결선이 0 건이라 오늘은 공허하게 참이다. 「승인 거부된 메모리 접근은 그
    순서 토큰을 실패 완료로 닫는다」는 메모리 파이프 착지의 선행 조건이다(B.5 신설 행 「승인 거부된
    메모리 접근의 순서 토큰 — 실패 완료로 닫기」 `b-gaps.typ:2129`).
- 장치는 타임아웃을 두지 않는다. **정지가 영구가 되지 않게 할 책임은 Y4 에 있다.**
  Y4 는 임대 메모리를 미리 핀(pre-pin)해 두어 언제나 채울 수 있게 한다. 사전 채움은
  상주를 보장하지 않으며 성능 힌트일 뿐이다(형상 비노출 표면).
- `0xC00` 기입 열(VPN → FRAME → COMMIT)을 쓰는 모든 경로 — 미적중 채움 · 회전 뒤 기입 ·
  회수 중 채움 — 는 **장치 전역 락 하나로 직렬화**한다(스테이징이 장치에 하나).
- **`[6]` 귀속 락 (`hiu_cfg`, HIU 마다 하나).** `FAULT_STATUS[6]` 은 장치에 하나뿐인 sticky 다. 그래서
  `[6]` 을 예상하거나 판정에 쓰는 구간 — §2.3 ⑵–⑷(flush · 기준선 확인 · 재시도 포함) · §2.4 2 의 창 기입부터
  3 의 기준선 대기 · `0xE14` 되읽기 · `[6]` 폴링 · 귀속 · 해제까지 · §2.7 전역 구성 창 · §2.5 초기화 — 는 이 락
  아래 직렬화한다.
  마스크 락(`0xEA0` 창)은 그 안에서 쥔다. 일반 fault 처리기는 `[12]` 처럼 `[6]` 도 락 보유자에게 넘기고
  해제하지 않는다. 그래야 결속되지 않은 파티션의 회전과 전환이 겹쳐도 v1.0 `0xE14` 경합 거절의 `[6]` 이
  회전 쪽에서 Y4 결함으로 읽히거나 기준선 해제로 지워지지 않는다.

### 2.3 임대 회전 (정본 E.9 6항, `e-defined.typ:1538-1555`; H1-3 · H1-4)

⑴–⑷ 는 *그 파티션 p 에만* 걸린다(`e-defined.typ:1546` 「*하나*」). 전역 flush 는 없다.

1. **드레인 (정본 ⑴ = 3.7.2 드레인 의무; 기계에 드레인 모드는 없다).** p 가 ACTIVE_PART
   인지에 따라 갈린다(결속 전환이 언제나 §2.4 의 판정을 거친다는 전제).
   - **p == ACTIVE_PART** — 투입하는 것이 p 뿐이므로 「그 파티션에 대한 투입을 멈춘다」
     문면 그대로이고, 관측은 장치 전역 `DRAIN_ALLZERO` 로 한다.
     1. Y4 가 p 에 대한 **투입을 멈춘다** — 단일 capability invocation 안의 직렬화가 그
        수단이다.
     2. **드레인 루프** — `DRAIN_ALLZERO` 가 설 때까지 되풀이한다(유계):
        - 서 있는 미적중 정지를 채운다(§2.2 — 회수이므로 옛 임대 사상 또는 거부 채움).
          정지한 요청은 드레인 정의역 ①에 남아 `DRAIN_ALLZERO` 를 0 으로 붙잡는다
          (정본 B.5 「E.3 미적중 정지가 드레인 안에서 갖는 처분」 갈래 ⑴, `b-gaps.typ:1505-1529`).
        - 완료 링을 비운다(`0x30C` CQ_HEAD 전진, E.6 4항) — `DRAIN_ALLZERO` 는 CQ_OCC 를
          포함한다.
        - 마지막 조각을 잃은 재조립 문맥(`DRAIN[4]`)을 `0xF40` 태그 지정 소거로 닫는다
          (`03-hiu.typ:1336-1339`).
     3. 루프 뒤 `0xE10` 해제를 한 번 한다(「항목 기입 → 해제」).
     - 채우기 전에 `0xE04[15:8]` == p 와 `0xE0C` == 0 을 확인한다(어기면 fail-closed, §1.2.1).
   - **p ≠ ACTIVE_PART** — 결속이 p 를 떠날 때의 판정으로 ⑴ 은 이미 충족돼 있다. p 의
     일은 정의역 · 완료 큐 · 링 어디에도 없다. 살아 있는 임대의 투입은 멈추지 않는다.
     (이 분기는 3.7.2 「드레인 의무의 범위」(`03-hiu.typ:1215-1245`)에 기댄다: 결속되지
     않은 파티션의 파티션 범위 구성(flush · 키 · 논스 · 재키잉)은 전역 드레인을 요구하지 않고,
     결속된 파티션의 그것과 전역 구성은 장치 전역 드레인을 유지한다. `0xC00` 항목 기입은 결속
     여부와 무관하게 구성 교체가 아니다(V=1 채움 · V=0 철회). 전역 구성 기입은 §2.7 창에서 한다.)
2. `hiu_cfg` 락(§2.2)을 쥔 뒤 `0xE00` XLATE_FLUSH ← p — flush 거절의 `[6]` 도 이 락 안에서 ⑶ 진입 전 기준선이 판정한다. 그 파티션의 항목이 전부 무효가 된다. p 를 래치한 스테이징의
   유효도 내린다.
3. `0xEA0` MASK_PART ← p. `0xE80`–`0xE9C` 에 새 키 8 워드, `0xEA4`–`0xEB8` 에 새 논스
   6 워드를 기입한다. 이 열(⑶ → ⑷)은 장치 전역으로 직렬화한다(창이 하나).
4. `0xEC0[9]`(재키잉 수락 가능)이 설 때까지 기다린 뒤 `0xEBC` MASK_REKEY ← p.
   - 완료 관측: **`0xEC0[8]`(엔진 busy)이 내려갈 때까지 기다린 뒤**, 그 파티션 준비 비트와
     `0xF80` 의 `[6]` · `[12]` · `[13]` 을 확인한다(정본 E.9 ⑷ `e-defined.typ:1543-1544` —
     발화 전 `[9]` 확인 포함).
   - 근거 문면(정본 `e-defined.typ:347` · `:1544`): 「재키잉이 시작된(…) `MASK_REKEY` *뒤에 버스 수락된*
     MASK_STATUS 읽기는 완료 전까지 `[8]` = 1 을 본다」. 준비 비트 · `[13]` · IDLE 은 같은 FINAL
     에지에 갱신되고, 「`[8]` = 0 을 본 MASK_STATUS 읽기 *뒤에 수락된* FAULT_STATUS 읽기는 최종 `[13]`
     을 본다」. Y4 는 `0xEC0` 읽기(`[8]` = 0) 뒤에 `0xF80` 을 읽는다.
   - 처분: ⑶ 진입 전에 `0xF80` 의 `[6]` · `[12]` · `[13]` 이 0 이어야 한다 — sticky 라서, 서
     있으면 앞 사건으로 처분하고 `0xF84` 로 해제한 뒤 진입한다. 준비 = 1 ∧ `[6]` · `[12]` ·
     `[13]` = 0 일 때만 성공. `[6]` 은 §2.4 3 과 같은 원리로 판정한다 — ⑶ 진입 전 기준선의 `[6]` 은 앞
     기입(⑵ flush 등) 뒤 `[6]` 가시 대기 상한을 거친 뒤 읽고, ⑷ 성공 판정의 `[6]` 은 ⑷ 발화 뒤 같은 상한이
     지난 뒤의 FAULT_STATUS 읽기로 본다(정본이 읽기 순서를 거는 것은 최종 `[13]` 뿐이다 — `e-defined.typ:1544`).
     준비 = 0 · `[13]` · `[9]`/`[8]` 대기 시간 초과면 `0xF84` 로 해제한 뒤
     ⑶ 부터 유계 재시도하고, 재시도가 소진되면 그 파티션을 격리한다. 재시도 경로의 해제는 `[13]`
     만 한다(§1.2.1 (C)) — `[6]` 은 Y4 결함으로, `[12]` 는 §2.6 으로 재시도 없이 이탈한다. 재시도의 ⑶ 은 같은 키와
     *새* 논스(`NonceAllocator.next()`)를 기입한다 — 쌍 유일성(§3.2)이 재시도 경로에도 서게
     한다. `[12]` 면 재시도하지 않고(같은 논스로 ⑶ 을 다시 하면 같은 `[12]` 가 결정론적으로
     다시 선다) §2.6 으로 원인을 귀속한다. `[6]` 이면 Y4 결함(값 오류).
   - 모든 대기는 유계다. 드레인 시간 초과는 flush 로 진행하지 않는다(P10 — 장치는 타임아웃을
     두지 않는다). p == ACTIVE_PART 회전의 드레인 시간 초과는 결속을 옮길 길이 없으므로
     §2.4 와 같이 **장치 전체 격리**(§2.6 의 reset 조건)다.

- **Y4 측 선택:** 새 임대의 항목 기입(`0xC00`)은 ⑷ 뒤에 한다. ⑵ 뒤 첫 기입은 새 열의
  처음(VPN)부터다 — flush 가 스테이징을 비우기 때문이다.
- 순서를 어긴 구간의 요청은 **정지되지 않고 통과**하며, `[11]` 이 사후에 알린다
  (`e-defined.typ:1551-1555`). 장치 자체는 fail-closed 가 아니라 loud 다 — fail-closed 는
  Y4 정책(P10)이다.
- `DRAIN_ALLZERO = 1` 의 뜻은 「이 정의역이 비었다」이지 「장치에 비행 중인 일이 없다」가 아니다
  (`b-gaps.typ:1984-1985` — 그 정의역은 드레인 정의역 여섯 + 완료 큐 점유다, `e-defined.typ:270-271`). 정의역 밖 실행 주체를 두는 확장이
  들어오면 다시 따져야 한다(정본 B.5 조건부, `b-gaps.typ:1979-2004`).
- 회전마다 에포크를 올리는 호스트 의무(규약 미정, B.5)는 §5.3-6 데이터 경로 묶음에서
  정한다.

### 2.4 임대 전환 — 결속 교체 (`0xE14`, 합의 2026-10-09)

스케줄러가 패브릭을 다른 살아 있는 임대에게 넘길 때다. flush · 재키잉은 없다. 전역 구성 기입은
이 절차의 창(③ 앞)에서 한다(§2.7).

1. 지금 결속된 임대 cur 에 대한 투입을 멈춘다.
2. 드레인 루프(§2.3 ⑴-2 와 같음). 미적중 정지는 *살아 있는 임대의 실제 사상*으로 채운다.
   사상이 없는 VPN 은 거부 채움으로 풀고, `DRAIN_ALLZERO` 관측 뒤 그 VPN 들의 V=0 무효화를
   한 번에 한 다음 `0xE10` 해제를 한 번 한다(「항목 기입 → 해제」, §2.2).
   - 이 창에서 회수 대기 프레임 일괄 처리와 전역 구성 기입을 한다(§2.7).
3. **기준선.** 창의 마지막 기입 뒤 `[6]` 가시 대기 상한만큼 기다린 다음 `0xF80[6]` = 0 을 확인한다(창의 전역
   구성 기입이 거절되지 않았다는 검증 겸 기준선 — 서 있으면 Y4 결함). 기입 거절의 `[6]` 도 보이는 시점이 정본에
   없으므로 「유계 대기 뒤 0」을 기준선으로 삼는다. 그 뒤 `0xE14` ← next(RMW — 되읽은 `[31:8]` 그대로 · `[7:0]` =
   next, next ≠ cur — Verus 사전조건)를 쓰고, 다른 구성 접근 없이 곧바로 되읽는다.
   **판정은 이 되읽기의 (A, D) 로만 한다** — `r[7:0] == next ∧ r[8] == 1(A) ∧ r[9] == 1(D)` 인가.
   - **`[6]` 처리 — 분기보다 먼저.** A = 0 이면 되읽기 응답 *뒤에* `0xF80[6]` = 1 을 유계 폴링으로 확인하고,
     `0xE14` 몫으로 귀속해 `0xF84` 에 `[6]` 하나만 쓴다(`1 << 6`). 폴링이 소진되면 거절의 loud 가 없는 것이다 —
     장치 모순 → `DeviceFault`. A = 1 이면 `[6]` 을 기대하지 않는다. 폴링 상한(= 위 가시 대기 상한)은 플랫폼
     레지스트리 값이다(`hw_mechanism_abstraction.md` §2) — 정본은 거절 = `[6]` 만 보장하고 `[6]` 이 `0xF80` 에
     보이는 사이클은 걸지 않으며, Y4 는 절대 사이클 수를 ABI 로 삼지 않는다. Y4 는 판정 사이클 정지(재구현은
     HIU 접수 · 정렬 `0xE14` 접근만 정지한다 — 3.9 `03-hiu.typ:1556`)에도 기대지 않는다. WT 에는 v1.x 비차단
     명확화로 「거절된 `0xE14` 기입의 `[6]` 은 그 기입 뒤 수락된 `0xE14` 읽기 뒤에 수락된 FAULT_STATUS 읽기에
     보인다」를 제안한다.
   - **(A, D) 를 이 기입의 결과로 읽는 근거** — 직전 버스 수락된 `0xE14` 기입이 이 기입이다: (i) `hiu_cfg` 락
     아래 Y4 가 유일한 기입자다 · (ii) 정렬 32b 전폭 기입이다(비정렬 `0xE15`–`0xE17` 은 정의역 밖 — A · D · 결속
     불변, 그 뒤 `[8]`/`[9]` 는 앞 기입의 값이다, `e-defined.typ:332` 3항 · §1.2.1 (C)) · (iii) 기입과 되읽기 사이에
     reset 이 없다 · (iv) 재구현 구조상 정렬 되읽기는 판정 사이클 뒤에 수락된다(3.9 `03-hiu.typ:1556` — 판정 사이클에 정렬
     `0xE14` 접근이 정지한다 · WT 착지 통지 §1; 사실이지 규범이 아니다).
   - A=0 ∧ D=1 ∧ 결속 == cur: 값 거절 — Y4 결함(장부 오류)(정본 `e-defined.typ:332` 3항).
   - A=0 ∧ D=0(유효 값): v1.0 에서는 외부 원천과의 경합일 수 있다 → 유계 재드레인 재시도 →
     소진 시 장치 격리. 재시도는 2 의 드레인 루프 · 거부 VPN 의 V=0 · `0xE10` 만 다시 돈다 — 회수 · 전역 구성
     기입은 되풀이하지 않는다(`hiu_cfg` 는 쥔 채). 그 뒤 기준선(유계 대기 뒤 `[6]` = 0)을 다시 확인하고 `0xE14`
     기입으로 간다. 링 소비 회로가 착지한 판부터는 Y4 결함(투입 정지 실패 또는 드레인 오판)으로 되돌린다.
   - 그 밖의 조합(A=1 ∧ 결속 ≠ next · A=1 ∧ D=0 · A=0 ∧ 결속 ≠ cur)은 장치 모순 → `DeviceFault`.
   - Verus: `lease::active_part::switch_outcome` · `switch_outcome_exhaustive`(네 결과는 서로 배타이고 모든
     되읽기를 덮는다) · `rejection_implies_fault6_expected` · `after_readback`(A = 0 인데 상한 안에 `[6]` 이 없으면
     `DeviceFault`).
4. 새 임대의 투입을 재개한다.

- 전환 드레인이 시간 안에 끝나지 않으면 결속을 옮길 길이 없다. 처분은 파티션 격리가
  아니라 **장치 전체 격리**다. reset 은 플랫폼이 증명한 경로가 있을 때만 한다(§2.6).
- **v1.0 한계:** HP-3 때문에 명령 링 데이터 경로가 없고 일의 원천은 외부 제시다
  (`e-defined.typ:716`). Y4 는 그 원천을 멈출 수 없으므로, v1.0 에서 ACTIVE_PART 의
  격리는 장치 판정만으로 서지 않는다(판정 뒤 도착하는 옛 임대의 일). 그래서 v1.0 의
  ACTIVE_PART 는 내부 포트 결속을 MMIO 로 바꾸는 표면이고(정본 `e-defined.typ:332` · 3.7.2 「v1.0 의 결속은
  격리를 주장하지 않는다」 `03-hiu.typ:1311-1320` — 재구현의 내부 포트는 W4 에서 은퇴했다), Y4 는 mock 으로만
  검증한다. 격리 주장은 투입 정지 수단(명령 링 소비 회로)이 착지한 판에서 한다(WaveTensor 동의).

### 2.5 부팅 순서

**reset 뒤 소거 구간 (HP-5):**
- 선택자 표 소거(`0xF08[0]` = 0) 동안 정렬된 FP_PROG/FP_BIND(`0xF00`/`0xF04`) 쓰기는 정지한다
  (정본 — `03-hiu.typ:1126-1129`; `0xF08[0]` 의 뜻은 `e-defined.typ:462-463`). **(a)** `0xF00`–`0xF3F` 의
  읽기는 응답하고 `0xF08[0]` 이 폴링 대상이다. 비정렬 쓰기와 `0xF08` 쓰기는 즉시 거절 + `[6]` 이다
  (정본 reset 값 규범 6항 `e-defined.typ:216`).
- 사상표(`0x400`–`0xBFF`) 소거 동안 쓰기는 정지하고 읽기도 기다린다. **(b) 소거 완료 비트는
  v1.x 로 미뤄졌다**(B.5 — 두 소거가 오늘 같은 길이인 것은 우연이다). 「사상표 소거 sweep 은 reset 마다
  처음부터 다시 돌고, reset 해제 뒤 ≤ `2^LNID_W` 장치 사이클 안에 끝난다」는 v1.0 규범이다(정본 reset 값
  규범 5항 `e-defined.typ:216`). 정지 길이는 2^16 사이클 — 1 GHz 에서 65.5 µs, 100 MHz 에서 655 µs 다.
- 수락되지 않은 접근은 효과도 응답도 없다.

**장치 reset 사실 (WaveTensor 2026-10-09 확인):** 재구현의 reset 은 최상위 비동기 핀 하나이고
maskValid · 키 · 논스 · HIU 파이프 단 valid(미적중 정지 포함) · 채움 대기 · 스테이징 · 변환
유효 비트 · FAULT sticky 전부 · MASK_PART 를 지운다. 항목 본체는 지우지 않지만 유효 비트가
가린다. **FLR 을 이 핀에 잇는 것은 플랫폼 몫이라 미정**이다. reset 값은 정본 규범이 됐다(「reset 값」
`e-defined.typ:216`): `0xEC4` = 0 · `0xE14` = 0 · FAULT_STATUS · `0xE04[1]` · `0xF8C` CAP_STATUS ·
`0x320` IRQ_STATUS 의 sticky 전부 = 0 · 페이지 소유권 표 전 페이지 호스트 소유 · 사상표 소거 재시작. 그래도
호스트 재부팅이 장치 reset 을 뜻한다고 가정하지 않는다.

**초기화 순서 (Y4 이행 — 무조건 수행):**
1. `0xFFC` · `0xFF8` 를 읽는다(major 1 결속, §1.4).
2. (`hiu_cfg` 락 아래 — 초기화 전체.) 셋으로 나뉜다:
   - 2a. `0xF80` · `0xEC4` · `0xE04`/`0xE08`/`0xE0C` · `0xF8C` 를 읽어 「이전 부팅 잔여」로 기록하고, 읽은
     FAULT 비트 전부를 `0xF84` 로, CAP_STATUS 비트를 `0xF90` 으로 해제한다 — 부팅 잔여는 이번 부팅의
     귀속 대상이 아니다(§1.2.1 (C) 의 `[12]` 해제 금지의 예외; 앞 부팅의 능력 부재를 첫 임대의 것으로
     오인하지 않게). 이 해제는 부팅마다 한 번만 한다.
   - 2b. **드레인 루프를 `DRAIN_ALLZERO` = 1 까지 돈다**(§2.3 ⑴-2 와 같음 — 유계, 소진 시 장치 격리;
     장치가 reset 되지 않았다면 남은 일이 있을 수 있다). 루프의 미적중 정지는 거부 채움(V=1 · 권한
     0)으로 푼다.
   - 2c. 루프 뒤 `0xF80` 을 다시 읽는다: `[4]` · `[19]` 비소유 프레임 접근(§1.3)은 「부팅 잔여」로 기록하고 그
     비트만 해제한다. 그 밖의 비트는 §1.3 대로 처분한다.
   3–5 는 이 관측 뒤에 한다.
3. 모든 실재 파티션에 `0xE00` flush 를 쓴다(E.9 4항 「키 변경은 해당 파티션의 flush 와 함께만
   일어난다」, `e-defined.typ:1524`).
4. `0xEC0[8]` = 0 을 기다린 뒤(유계), 파티션마다 `0xEA0` MASK_PART ← p 로 두고 I3 경로
   (`NonceAllocator.next()` · KDF)의 새 키 · 논스를 기입해 마스크 유효를 내린다(`:339` · `:343`).
   장부에는 (논스, 이번 부팅, 마스크 유효 = 거짓)을 적는다. 그 뒤 `0xF80[12]` = 0 ∧ `0xEC0[8]` = 0 ∧
   `0xEC0[7:0]` == 0 을 확인한다. **재키잉은 임대 발급 때로 미룬다** — 재부팅을
   넘은 논스 잔여가 `[12]` 를 만들려면 상대 파티션이 마스크 유효여야 하는데, 이 순서 뒤에는
   어느 파티션도 마스크 유효가 아니다(정본 `e-defined.typ:345` — `[12]` 는 마스크가 유효한 *다른* 파티션
   q ≠ p 만 비교한다. RTL `rtl/…/mask/MaskUnit.scala:365-366` 과 일치).
5. 3 의 flush 에지 뒤 `DRAIN_ALLZERO` 를 다시 관측한다(§2.7 규칙 3 — 아니면 2b 로, 유계). 그다음 앞
   부팅의 소유 페이지를 회수한다 — 장부가 없으므로 장치 버퍼 풀(PA < 2^44)의 프레임을 `OWN_IDX` /
   `OWN_STATUS` 로 훑어 장치 소유인 것을 `OWN_CLR` 한다. 사상표 · step 접근(`0x400`–`0xBFF` ·
   `0xF00`/`0xF04`)은 마지막에 둔다: LNID(`0x400`–`0x7FF`) · LBID(`0x800`–`0xBFF`) 전 엔트리에 V=0 를
   기입하고 Y4 장부의 초기 상태를 「전 엔트리 무효」로 둔다(`lbid_all_invalid_ok` — §2.8).
   `0xF08[0]` 을 폴링하고, 사상표 첫 접근은 플랫폼이 준 지연(≥ 2^16 / f_dev_min,
   `hw_mechanism_abstraction.md` §2 레지스트리)으로 게이트한다.
6. `0xE14` ← p0(첫 임대의 파티션, RMW 꼴). 부팅 기입은 §2.4 전환이 아니라 결속 확립이다 — 장치
   결속이 미지이므로 next ≠ cur 사전조건을 걸지 않는다. 되읽어 `r[7:0] == p0 ∧ r[8] == 1 ∧ r[9] == 1`
   을 요구한다 — 같은 값이어도 D = 1 이어야 한다(flush 에지 뒤의 드레인 관측). 기입 전 기준선과 `[6]` 처리는
   §2.4 3 과 같다 — 유계 대기 뒤 `[6]` = 0 을 확인하고 기입하며, A = 0 이면 되읽기 뒤 `[6]` 을 확인 · 귀속 ·
   해제한다. A = 0 ∧ `[7:0]` == p0 와 A = 1 ∧ `[7:0]` ≠ p0 는 장치 모순 → `DeviceFault`(같은 값 기입은 D 와
   무관하게 A = 1 이고 거절은 결속을 바꾸지 않는다 — `e-defined.typ:332`). A = 0 ∧ D = 1 ∧ `[7:0]` ≠ p0 는 값
   거절 — Y4 결함(p0 장부 오류)이다. D = 0 이면(A = 0 ∧ `[7:0]` ≠ p0, 또는 A = 1 ∧ `[7:0]` == p0) 2b 의 드레인
   루프(와 2c)로 돌아가 재드레인한다 — 2a 의 일괄 해제는 되풀이하지 않는다(유계, 소진 시 장치 격리). 이
   확인 전에는 어느 프레임도 `OWN_SET` 하거나 사상하지 않는다. 첫 임대의 I4 ⑷ 성공 전에는 투입을 열지 않고, 그동안 결속 파티션의 미적중은 거부 채움으로 푼다 — 그 `[4]` 는 첫 임대 ⑶ 진입
   전에 읽어 부팅 몫으로 해제한다.

### 2.6 `[12]` 원인 귀속 (Y4 이행 · 캡처 워드 `0xEC4` 는 정본 · RTL W1 `9b6eee6`)

`[12]` 는 「마스크가 유효한 다른 파티션 q 와 재키잉하는 p 가 같은 논스를 지고 있다」는 *건전한* 신호다
(`e-defined.typ:1568-1569`). p 자신은 비교에 들지 않는다(`:345` — `[12]` 는 마스크가 유효한 *다른* 파티션 q ≠ p
가운데 논스가 p 의 *새* 논스와 같은 것이 있을 때 선다). 재키잉 발화 시점의 p 는 키 · 논스 기입으로 마스크
유효가 이미 내려가 있으므로(`:339` · `:343`) 비교되는 것은 p 의 새 논스와 살아 있는 q 의 논스다. 발화 시점에
p 의 새 논스와 마스크 유효인 q 의 논스가 같으므로 「논스는 파티션마다 다르다」의 위반은 이미 실재한다
(`:1568-1569`). 재키잉은 `[12]` 와 무관하게 완료되므로(`b-gaps.typ:2085`) 그 완료로 마스크가 유효한 두
파티션(p, q)이 같은 논스를 지게 된다 — 마스크 유효인 두 파티션의 논스는 서로 다르다는 Y4 장부
불변식(`lease_capability.md` I3 부속)의 위반도 장치 안에 실재하게 된다. 물을 것은 그 상태를 누가
만들었는가다. 원인이 Y4 쪽이면 Y4 의 검증된 장부가 틀린 것이고, 장치 쪽이면 Y4 의 상태는 멀쩡하다. 처분이 달라야 한다.

**Y4 논스 장부.** Y4 는 실재 파티션마다 「지금 장치에 기입한 논스 · 기입한 부팅 · 마스크
유효 여부」를 기록한다(`lease_capability.md` I3). §2.5 초기화 뒤에는 어느 파티션도 마스크 유효가
아니고, 마스크 유효가 되는 것은 이번 부팅에 Y4 가 재키잉한 파티션뿐이다. 키 · 논스 기입(§2.5 4 의 중화
기입이든 I4 step 3 의 재키잉이든)은 그 파티션을 (기입 논스, 이번 부팅, 마스크 유효 = 거짓)으로 적고,
⑷ 완료 확인이 성공해야 마스크 유효 = 참으로 적는다. 장부 불변식은 둘이다 — 마스크 유효인 두 파티션의
논스는 서로 다르고, 재키잉 발화 시점의 p 의 기입 논스는 장부상 마스크 유효인 모든 q ≠ p 의 논스와 다르다.

**귀속 순서** (`[12]` 를 본 즉시, 그 HIU 의 투입을 멈추고 마스크 락을 쥔 상태에서 — FAULT_CLEAR
보다 먼저):
1. `0xEC4` 를 한 번 읽는다(p · 비트맵 · `[16]` 을 한 읽기로). 먼저 `[16]` 을 본다 — `[16]` = 0 이면
   정본 불변식 `[16]` ⇔ `[12]`(`e-defined.typ:347`)의 위반이다. Y4 는 귀속 중 `0xF84` 를 쓰지
   않고 내부 해제선은 제품 결선에서 0 으로 묶이므로, 이것은 장치(또는 플랫폼 결선)의 계약 위반 —
   **장치 쪽**으로 기록하고 끝낸다. `[16]` = 1 이면 p == Y4 가 재키잉한 파티션 ∧ 비트맵 ≠ 0 ∧ 비트맵
   ⊆ 실재 파티션 − {p} 를 검증하고, 어기면 **장치 쪽**. (bit p = 0 은 정본 `e-defined.typ:345` · `:347` 의
   약속이다 — 실재 파티션 수 이상의 비트도 0 이다.)
2. 장부에서 (i) p 의 새 논스(이번 `MASK_REKEY` 직전에 Y4 가 기입한 값)와 같은 논스를 지닌, 장부상 마스크
   유효인 q ≠ p 가 있거나 (ii) 마스크 유효 파티션끼리 같은 논스가 있으면 **Y4 의도 결함**
   (`NonceAllocator` · 장부 결함). (i) 이 필요한 까닭은 재키잉 중인 p 가 장부상 마스크 무효라 (ii) 만으로는
   p 의 새 논스가 비교되지 않기 때문이다.
3. 없으면:
   - 캡처의 겹친 파티션 가운데 장부상 키 · 논스를 이번 부팅에 Y4 가 기입한 적이 없는 q 가 하나라도 있으면
     **Y4 절차 결함** — 부팅 중화(§2.5 4)를 건너뛰었거나 그 기입을 장부에 남기지 않았다.
   - 모두 기입됐으면 **장치 쪽**: 기입 경로 · 저장 · 비교기 결함. 2 를 지났으므로 장부상 마스크 유효인 q 의 논스는
     p 의 새 논스와 다르고, 장부상 마스크 무효인 q 가 캡처에 들었다면 장치가 Y4 가 주지 않은 마스크 유효를
     주장한 것이다. 논스는 WO 라 되읽을 수 없으므로 Y4 기입 경로 결함과 장치 결함은 더 나누지 못한다. 둘 다
     Y4 의 검증된 장부 밖이다.
   - 이 순서는 전체(total)다 — 모든 `[12]` 가 Y4 의도 · Y4 절차 · 장치 쪽 가운데 하나로 귀속되고 「귀속 불가」는
     없다(Verus `lease::nonce::nonce_dup_origin` · `nonce_dup_origin_total`). 장부에 보이는 충돌은 장치 쪽으로
     가지 않는다(`y4_collision_never_blamed_on_device`).

**처분** (`proofs/verus/src/error.rs` `fault_disposition`):

| 원인 | 오류 | 처분 |
|---|---|---|
| Y4 의도 결함 · Y4 절차 결함 | `LeaseInvariant` | 하이퍼바이저 정지(fail-stop) — 다른 임대의 키 · 논스 장부도 믿을 수 없다 |
| 장치 쪽 · 귀속 불가 | `DeviceFault` | 장치 격리 — 그 HIU 의 모든 임대 회수 · 결함 표시. 하이퍼바이저와 다른 장치는 계속 돈다. 귀속 불가는 기록에 「원인 미귀속」으로 남긴다(v1.0 장치의 `[12]` 에서는 생기지 않는다 — `[19]` 비소유 프레임 접근에서만 쓴다, §1.3) |

**장치 격리의 reset 조건 (사용자 결정 2026-10-09):** 장치 reset 은 Y4 가 부를 수 있는 기본
동작이 아니다(FLR 결선 미정). 플랫폼이 증명한 reset 경로(`hw_mechanism_abstraction.md` §2 레지스트리)가 있을 때만 reset 하고, 없으면 장치를
결함으로 표시해 재부팅이나 증명된 reset 까지 재사용하지 않는다(사용자 결정). 주의: 호스트 재부팅은
장치 reset 이 아니고 §2.5 초기화는 장치 결함을 시험하지 않는다. 그래서 지속 결함(비교기 · 저장
결함 등)을 지닌 장치는 재부팅 뒤 다시 쓰이다가 같은 귀속으로 다시 격리될 수 있다 — 결함 이력을
부팅을 넘어 보존할지는 v1.0 이후 과제다. reset 전에는 `0xF80` · `0xEC4` · `0xEC0` ·
`0xE04`/`0xE08`/`0xE0C` · `0x360`–`0x37C` · `0xF8C` · `0x320` 을 기록에 스냅샷한다(reset 이 sticky 와
캡처를 지운다 — 정본 reset 값 규범 `e-defined.typ:216`).
reset 뒤에는 Y4 의 소프트웨어 거울을 reset 상태로 되돌리고(`active_part` = 0 · 장부의 마스크 유효
전부 거짓 · 스테이징 빔 · MASK_PART = 0) §2.5 초기화를 다시 한다.

- 귀속은 진단이지 복구가 아니다. 어느 경우든 그 임대는 실패다.
- Verus: `fault_disposition_separates_origin` — 하이퍼바이저 정지는 원인이 Y4 쪽일 때와만
  동치이고, 장치 쪽 · 귀속 불가는 정지에 이르지 않는다.

### 2.7 사상 철회 · 프레임 회수 · 전역 구성 창 (Y4 이행 — 사용자 결정 2026-10-09)

**왜 필요한가.** V=0 와 flush 는 커밋 에지 뒤에 판정되는 조회에만 효력이 있다(결과 (b) · 정본 3.7.2
「철회의 효력 범위」 `03-hiu.typ:1322-1334`). 판정 래치 아래에서는 V=1 덮어쓰기(프레임 교체 · 권한 축소)도 같다 —
에지 전에 판정된 요청은 옛 프레임 · 옛 권한으로 끝까지 간다.
그런데 승인 단의 소유권 판정은 프레임 전역이고 파티션을 보지 않는다(`rtl/…/hiu/HiuPipeline.scala:404-410`
owner.frame → devOwned). 그러니 V=0 직후 그 프레임을 다른 임대에 사상하면(장치 소유
유지), 이미 판정된 옛 요청이 소유 검사를 통과해 테넌트 간 접근이 된다. V=0 직후 `OWN_CLR` 하면
옛 요청이 `[19]` 비소유 프레임 접근을 세우고(정본 해설 `e-defined.typ:529` 가 이 경우를 예로 든다), 승인을 지난
소비 단 접근은 이 검사로 막히지도 않는다.

**규칙:**
1. 사상 해제(unmap · remap)는 `xlate_staging` 락의 *같은* 임계 구역에서, Y4 장부(`dva_map`)에서
   먼저 빼고 그다음 V=0 를 커밋한다 — 그 사이 미적중 채움이 옛 사상을 V=1 로 되살리지 못한다.
   - 1a. 살아 있는 임대의 사상 *추가*(map · remap 의 새 프레임)는 그 임대의 소유 페이지(이미 `OWN_SET`
     된 장치 소유 프레임)에서만 즉시 한다. 그 밖의 프레임은 다음 전환 창의 `OWN_SET` 뒤에 사상한다
     (`OWN_SET` 은 전역 구성 — 승인 단은 장치 소유가 아니면 거부한다, `HiuPipeline.scala:410`).
   - 1b. **권한 축소**(같은 VPN · 같은 프레임, 권한 비트 감소)는 `dva_map` 을 먼저 고치고 축소된 항목을
     커밋한다(V=1 덮어쓰기 — 결과 (a) 로 대체된다 — 또는 V=0 뒤 미적중 채움). 그 에지 전에 판정된 요청은
     옛 권한으로 끝까지 가므로, **축소에 기대는 동작(CoW · 쓰기 보호 · 이주 등)은 그 에지 뒤 `DRAIN_ALLZERO`
     관측 뒤에만 한다** — 처리는 규칙 3 의 자연 드레인 지점 또는 강제 드레인 창에서 한다. 프레임 교체는
     옛 프레임이 회수 대기에 드는 사상 해제다(규칙 1 · 2).
2. 뺀 프레임(remap 의 옛 프레임 포함)은 「V=0 에지 시각」과 함께 **회수 대기 목록**에 넣는다.
3. 그 프레임의 재사용(다른 임대 사상 · `OWN_CLR` · 할당기 반환)은 그 에지 *뒤에* `DRAIN_ALLZERO`
   를 관측한 뒤에만 한다.
   - **지연 회수:** 다음 자연 드레인 지점(§2.4 전환 · p == ACTIVE_PART 인 §2.3 회전의 ⑵ 뒤 재관측
     — `lease_capability.md` I4 2b)에서 일괄로 처리한다.
   - 목록에 상한을 둔다. 넘으면 강제 전환 · 드레인을 한다. 대기 중인 `OWN_SET` · 사상 추가(규칙 1a)
     · LNID/LBID · step 갱신이 있는데 유계 시간 `T_GCFG` 안에 전환이 없을 때도 같다. 전환할 다른 임대가
     없으면 *강제 드레인 창*을 연다(창 안의 순서: 회수 대기 `OWN_CLR` → 대기 `OWN_SET` · LNID/LBID
     (`lbid_write_ok`) · step): cur 투입 정지 → 드레인 루프(§2.4 2) → 회수 대기 처리 → 같은 값 `0xE14` ← cur
     탐침으로 `r[7:0] == cur ∧ A = 1 ∧ D = 1` 확인(D = 0 이면 재드레인) → 재개. 같은 값 기입을 쓰는
     유일한 절차이고 탐침 용도와 맞는다.
   - 회수 지연분은 임대 메모리 예산에 계상한다. 게스트 unmap 은 「프레임 해제는 비동기」 의미다
     (`y4_abi.md`).
4. 결속되지 않은 파티션(p ≠ ACTIVE_PART)의 해제는 결속 이탈 판정(D=1)이 p 의 일 0 을 보장하므로
   드레인 관측을 기다리지 않는다. 단 그 프레임이 장치 소유인 동안(지연된 `OWN_CLR` 이 남은 동안)은
   재사용하지 않는다 — 재사용은 다음 창에서 `OWN_CLR` 이 실행된 뒤다. 재결속 전에 V=0 가 끝나 있어야
   한다. 프레임 장부는 프레임마다 {사상됨 · 회수 대기(CLR 대기) · 호스트 소유} 상태를 진다.
5. Y4 프로토콜은 사상 철회로 인한 비소유 접근(`[19]`)을 만들지
   않는다. 관측되면 §1.3 처분이다.

**전역 구성 창.** 3.7.2 「드레인 의무의 범위」(`03-hiu.typ:1215-1245`)는 전역 구성을 오프셋으로
열거한다: `0x208`/`0x20C`(OWN_SET/OWN_CLR — 「소유권」은 `0x200` 페이지 소유권 표) · `0x400`–`0xBFF`
(사상표) · `0xF00`/`0xF04`(step) · `0x300`–`0x308`(CQ_BASE_LO/HI · CQ_SIZE) · `0x380`–`0x388`
(SQ_BASE_LO/HI · SQ_SIZE — 링 소비 회로 전에는 공허). 드레인 수행 · 관측 동작(CQ_HEAD · OWN_IDX ·
`0xE10` · `0xF40` 소거 · `0xF84` · `0xE14` 자신 · `0xEA0`)은 제외다. Y4 는 v1.0 에서 `0x300`–`0x308` ·
`0x380`–`0x388` 을 쓰지 않으므로(§1.2.1), 나머지 전역 구성 기입을 모두 「투입 정지 → `DRAIN_ALLZERO`
→ [창] → `0xE14` 기입 · 확인 → 재개」 창에 묶는다.
창 안의 순서는 회수 대기의 `OWN_CLR` 먼저, 그다음 새 임대의 `OWN_SET` 이다.
- 결속되지 않은 임대를 회수할 때의 `OWN_CLR` 은 다음 전환 창으로 미룬다. 그동안 페이지는 「회수
  대기 · 장치 소유」로 남는다. p 는 flush 됐고 어느 살아 있는 `dva_map` 에도 없으므로 도달할 수
  없다. E.9 6항에는 회수 단계가 없으므로(`e-defined.typ:1538-1544`) 미루어도 정본에 맞는다.
  p == ACTIVE_PART 회전은 ⑵ flush 뒤 드레인을 다시 관측한 다음 회수한다(규칙 3 — 철회 에지는
  flush 다).
- 새 임대의 `OWN_SET` 과 LNID/LBID 사상 · step 적재는 그 임대의 전환-진입 창에서 한다(임대는
  전환되기 전에는 돌지 않으므로 지연 손실이 없다). 그래서 사상표 · step 은 「전환마다 재적재」
  쪽으로 기운다.
- **v1.0 한계:** 외부 원천은 창 안에도 일을 넣을 수 있으므로, 창의 드레인은 관측 시점의 사실일 뿐 창
  내내 유지되지 않는다. `0xE14` 의 A=0 ∧ D=0 은 그 위반의 증거다. 회수 대기 프레임의 처리는 에지 뒤
  관측만으로 안전하지만, 새 임대의 전역 구성(OWN_SET · LNID/LBID · step)은 3.7.2 를 지켰다고 주장하지
  않는다 — v1.0 은 mock 검증이고, 주장은 소비 회로 착지 뒤에 한다(§2.4 v1.0 한계와 같다). 규칙 3 · 4 의
  안전성은 드레인 정의역이 승인 뒤 소비분을 덮는다는 전제 위에 선다 — 메모리 파이프 착지 선행 조건(B.5).
- **v1.x 후보 (Y4 제안 · B.5 신설 행 `b-gaps.typ:2168`):** 파티션별 「변환 펜스」 RO 비트 — 그 파티션의 마지막
  COMMIT · flush 에지 이전에 판정된 요청이 0 이다. 있으면 살아 있는 임대의 프레임을 전역 드레인 없이
  회수할 수 있다. 메모리 파이프 착지 시 승인 뒤 소비분까지 덮어야 한다.

### 2.8 LBID 사상표 대행 검증 (Y4 이행 — 사용자 결정 2026-10-09)

**왜 필요한가.** 정본 3.7.1 은 「유효한 두 LBID 엔트리가 겹치는 슬롯 구간을 지목하는 구성」을 다섯째 기입
시점 거절로 적지만, v1.0 장치는 그것을 판정하지 않고 수락한다(정본 「다섯째의 v1.0 처분」
`03-hiu.typ:1094` — 「겹치는 구성 아래에서는 FAB-4 와 그에 기댄 격리 성질을 보장하지 않으며,
*비겹침은 호스트 의무다*」, 규범 머리 「v1.0 장치에서는 처음 넷」 `:1068`). 재구현도 수락한다. 수락하면 두 조각열이 같은 슬롯에 착지해 FAB-4(소유 구간)가
런타임에 깨지고, 어떤 신호도 기입자에게 돌아오지 않는다. LBID 표는 장치 전역 한 벌이고 엔트리에 파티션
태그가 없다(`03-hiu.typ:996-999` — `[31]` V · `[15:8]` 구간 시작 · `[7:0]` 길이). 그래서 v1.0 에서
테넌트 간 겹침을 막는 것은 **Y4 의 대행 검증뿐**이다. 정본은 이 의무를 E.1.1 4항 귀결로 호스트에 지운다
(`e-defined.typ:208`). 거절 + loud 는 `[31:20]` 에 새 비트를 여는 판부터다.

**규칙:**
1. LBID 엔트리는 게스트가 직접 쓰지 못하고 Y4 가 capability 검증 뒤 대행한다(§1 머리).
2. 대행 기입마다 상주하는 유효 엔트리 전체에 대해 구간 `[start, start + len)` 의 서로소를 검사한다.
   같은 임대 안의 겹침도 거절한다(정본이 거절로 정한 구성이다).
3. 구간은 슬롯 용량 안이어야 한다(`start + len ≤ 슬롯 수`). 슬롯 수는 `0xFF8` 에 없으므로 플랫폼
   레지스트리 값을 쓴다(`hw_mechanism_abstraction.md` §2). 범위 밖 시작의 처분도 정본에 아직 없다(B.5).
4. 「길이」의 뜻(용량 임대인가 잉여인가)이 B.5 에서 열려 있으므로 `len` = 0 인 유효 엔트리는 쓰지 않는다
   — 어느 갈래로 닫혀도 보수적인 쪽이다.
5. **전환 · 회전마다 재적재:** 전환 창(§2.7)과 결속 파티션 회전의 ⑵ 뒤 재관측 창(`lease_capability.md`
   I4 2b)에서 나가는 임대의 LBID 엔트리(와 LNID 소유 엔트리)를 V=0 로 지우고(`lbid_invalidate_preserves`),
   들어오는 임대의 것만 싣는다. 결속되지 않은 파티션의 임대는 그 결속이 떠날 때의 전환 창에서 이미
   지워졌다. 상주 엔트리는 언제나 결속된 임대 하나의 것이다. 부팅 때는 전 엔트리를 V=0 로 시작한다(§2.5 5).
6. Verus 사전조건(`proofs/verus/src/lease/lbid.rs`): `lbid_write_ok` — 엔트리가 잘 형성되고 다른 어느
   상주 엔트리와도 겹치지 않음. `lbid_all_invalid_ok`(부팅 초기 상태) · `lbid_write_preserves` ·
   `lbid_invalidate_preserves` 가 표 불변식
   `lbid_table_ok` 의 보존을 증명한다.
- LNID 소유 표(`0x400`)의 기입 시점 거절 넷은 장치가 판정하고 `[6]` 에 접힌다 — Y4 는 그것도 미리 지키지만
  장치 거절에 기대지 않는다(§1.2.1 (A) 4).

### 3.1 회수 (release / expiry / revoke)

1. Y4 가 호스트 측 cap-table 에서 token 을 무효화한다.
2. §2.3 의 ⑴–⑷ 를 「빈 임대」로 수행한다. 빈 임대의 키·논스도 §3.2 와 같은 경로로
   짓는다(`lease_serial` 하나와 `NonceAllocator` 값 하나를 소비) — 그래서 §3.2 의 유일성이
   모든 회전을 덮는다. 이것이 옛 키를 덮어쓰는 Y4 측 이행이다. 장치 측 키 바이트 소거는
   정본에 규범이 없다(G1 — §5.1 항목 1).
3. 그 파티션의 소유 페이지를 `0x20C` 로 회수하고 그 임대의 LBID · LNID 엔트리를 V=0 로 지운다(§2.8 규칙 5) — p == ACTIVE_PART 회전이면 ⑵ flush 뒤 드레인을 다시 관측한 다음(§2.7 규칙 3), 아니면 다음 전환 창에서(§2.7).

### 3.2 `(키, 논스)` 유일성 — Y4 의무

- 논스: 단조 카운터 + 호스트 식별자 prefix (`lease_capability.md` I3).
- 키: 호스트 마스터 시크릿에서 `(파티션, 임대 일련번호)` 로 유도한다(KDF).
- 빈 임대도 같은 경로를 쓴다(§3.1).
- 신선도 근거: 호스트 마스터 시크릿은 **부팅마다 새로 짓는다**(임대는 재부팅을 넘지
  않는다). 그래서 카운터가 부팅마다 0 부터 다시 시작해도 쌍이 반복되지 않는다.
- 정본의 「논스는 파티션마다 다르다」(E.9 2항 첫 절)도 전역 단조 카운터로 함께 만족한다.
  단 한 부팅 안에서만 무조건 참이다 — 장치가 재부팅을 건너 reset 되지 않으면 옛 부팅의
  유효 논스가 남는다. 그래서 §2.5 의 초기화 순서(모든 파티션의 마스크 유효를 내림)가 이 절의
  전제다.
- 정본에는 호스트가 읽을 난수 워드가 없으므로, **장치 엔트로피에 의존하지 않는다.**
  마스터 시크릿의 엔트로피 원천은 호스트 쪽(`hw_mechanism_abstraction.md` 레지스트리)이다.

## 4. 인터럽트 / 폴링 (닫힘 — Y4 확정 답 3a, H3-6)

- **기본은 폴링이다.** 폴링 대상은 완료 링(`0x310` CQ_TAIL, `0x340` CQ_WINDOW), 미적중
  정지(`0xE04`), 그리고 fault(`0xF88` FAULT_SUMMARY → `0xF80`)다.
- 인터럽트는 **선택적 가속(opt-in)** 이다. `0x324` IRQ_MASK 를 RMW 로 갱신해 `[0]` 을 0 으로
  한다(§1.2.1). 원천은 완료 링 삽입이다(E.6).
- PCIe MSI-X 벡터 결선은 RTL 변경이 아니라 보드 층의 일이다. v1.x 에서 「완료 IRQ 의
  MSI-X 결선」으로 다룬다(H3-3 · H3-6).
- **fault → IRQ (G2, v1.x — 합의 2026-10-09):**
  - 처음 낸 형태(`IRQ_MASK[1]` reset 1, 0 = 켬)는 v0.1 문면의 드라이버에게 하위 호환이
    아니었다(`rtl/generated/CompletionUnit.sv:195` `io_irq = (irqSticky && (! irqMask))`
    — 레벨 출력). 그래서 Y4 는 별도 워드로 고쳤고 WaveTensor 가 받았다.
  - 형태: 미배정 `0x32C` FAULT_IRQ_EN(RW, `[0]` 1 = 켬, reset 0). `IRQ_STATUS[1]`(fault 요약,
    sticky)은 EN = 1 일 때만 *선다*. 이미 선 `[1]` 은 `IRQ_CLEAR[1]` 로만 내린다. `IRQ_MASK` 는
    건드리지 않는다.
  - WaveTensor 권고 넷 — 2 · 3 · 4 는 받는다. 1 은 세움 원천의 정의를 고쳤다(아래 — WaveTensor 수용,
    정본 B.5 G2 행 `b-gaps.typ:2096-2097` 에 기록):
    1. `[1]` 은 FAULT_STATUS 비트별 0→1 에서 세운다(SUMMARY 에지가 아니다 — 새 비트가 묻히지
       않게).
    2. 같은 사이클에 `IRQ_CLEAR[1]` 과 겨루면 세움이 이긴다.
    3. 드라이버 순서는 **`IRQ_CLEAR[1]` → FAULT_STATUS 읽기 → FAULT_CLEAR** 다(Y4 잠정안의
       결함을 바로잡음).
    4. 선 식은 `(STATUS[0] ∧ ¬MASK[0]) ∨ STATUS[1]` — EN 이 곧 fault 마스크다.
  - Y4 수정(수용됨): 1 과 2 를 함께 두면, FAULT_CLEAR 값에 든 비트가 해제 사이클에 다시 발화할 때
    1 로 남지만 0→1 에지가 없어 IRQ 를 잃는다(`rtl/…/Common.scala:336-337` StickyFault). 세움 원천을
    「흡수되지 않은 비트별 세움 사건 `set_b ∧ (¬old_b ∨ clr_b)`」로 정의해 달라. EN ← 0 이 대기 중인
    `[1]` 을 내리지 않고 EN ← 1 이 기존 FAULT_STATUS 로 `[1]` 을 세우지 않는다는 것도 적어 달라.
  - Y4 드라이버: FAULT_CLEAR 에는 처분한 비트만 쓴다(§1.2.1 (C)). `[12]` 는 일반 처리기가
    처분하지 않는다 — 마스크 락 보유자(§2.6)에게 넘기고 해제하지 않는다. 그 뒤 FAULT_STATUS 를
    다시 읽어, `[12]` 와 이미 넘긴 비트를 뺀 값이 0 이 아니면 유계 루프로 처리한다. EN ← 0 뒤
    `IRQ_CLEAR[1]`, EN ← 1 뒤 FAULT_STATUS 를 한 번 폴링한다. 주기적 FAULT_SUMMARY 폴링이
    뒷받침한다.
- 엔트로피 건강성은 `0xF80[17]`(sticky, `0xF84` W1C)로 폴링 관측한다. 재구현에는
  엔트로피원 유닛이 아직 없어서 상수 0 이다(`03-hiu.typ:1538` · `:1562`).

## 8. 이력 — v0 레지스터 표 (장치에 없음)

v0(2026-05)은 legacy 참조 구현을 기준으로 `BAR0 + 0x000`–`0x110` 에 다음 워드를 두었다.
재구현 장치는 합의 전 그 구간에 워드를 두지 않는다. 그래서 쓰면 거절 + `[6]`,
읽으면 0 이다(HP-1). 아래는 대응 관계만 남긴 것이다.

| v0 워드 | v0.2 처분 |
|---|---|
| `0x000` HIU_VIRT_ADDR · `0x008`/`0x00C` HIU_DMA_DATA_IN/OUT · `HIU_CTRL.dma_req` | 삭제 — 호스트 발행 DMA 단발 없음 (§2.1, G4) |
| `0x010` HIU_CTRL `ats_req`/`pri_req` · `0x014` HIU_STATUS `ats_resp`/`pri_resp` | 삭제 (기능 재도입은 v2 — §5.3, H2-1/2) |
| `HIU_CTRL.context_switch` (전 파티션 · shadow 동일 사이클 무효화) | `0xE00` 파티션별 flush + §2.3 회전 (H1-3). 전역 flush 금지 |
| `HIU_CTRL[7:6]` partition_id | 키 창 역할 → `0xEA0` MASK_PART · 값 → `0xE00`/`0xEBC` · 주소 → `0xC00` 창 기저 · 「현재 HIU 파티션」(요청 결속) 역할 → `0xE14` ACTIVE_PART (WT 제안, §2.4) |
| `HIU_CTRL[9:8]` interface_type | 요청 안 함. E.8 선택자 오프셋은 §5.3-7 |
| `HIU_STATUS.dma_ack` | 삭제 — E.6 통지는 완료 링 하나 (§4, H3-2) |
| `HIU_STATUS.access_granted` | 삭제 — 호스트 발행 DMA 단발 없음 (§2.1, G4); 승인 단계는 관측 표면이 아니다 |
| `0x018`–`0x028` HIU_SHADOW_* · `shadow_write_en` | `0xC00` 변환 항목 창 (H4-3; v0.2 는 형상 비노출 표면을 제안) |
| `0x040` HIU_CHACHA_KEY · `0x060` HIU_CHACHA_NONCE (한 벌) | `0xE80` 구역 파티션별 창 (H1-2) |
| `0x080` HIU_PHYS_ADDR (마스킹 전 RO) | 삭제 (H2-3) |
| `0x100`/`0x101`/`0x108`/`0x110` HIU_RNG_* · `trng_unhealthy` | 삭제 — 호스트용 난수 워드 없음. 건강성은 `0xF80[17]` (H3-5) |
| `0xFFC` HIU_ABI_VERSION (v0 = 옛 표의 판) | 같은 자리, 뜻 변경: 판 0 = 약속 없음 (§1.4, HP-2) |
| §2.1 「≈32 cycle · DUMMY_CYCLES=8」 | 삭제 — 절대 사이클 수는 ABI 아님 (§2.1, H4-1) |
| WO 정의 「read 시 0 또는 마지막 write 값 — 미정의」 | 읽기 0 (§1.2, H1-1) |
| 예약 영역 「write 무시 / read 0」 | 물려받은 구간 · 비정렬 · 소비 없는 RW 는 거절 + `[6]`. 표에 없는 오프셋만 무시 (§1.2, HP-1/3/4) |
| 「베이스 오프셋 `BAR0 + 0x0000`. 주소는 little-endian」 | 삭제 — 버스 배치·바이트 순서는 보드·어댑터 층 (§1 머리) |
